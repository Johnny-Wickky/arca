# Картинки в безопасном режиме

Цель: показывать картинки (отдельные файлы и картинки внутри документов) так же
параноидально, как всё остальное в Arca. Декодеры изображений — одна из самых частых
целей эксплойтов (libpng, libwebp CVE-2023-4863, ImageIO, Skia): поэтому **ни одна картинка из
недоверенного файла не попадает в системный декодер Android**.

## 1. Принципы

1. **Декодирование только в песочнице.** Пиксели строит библиотека `arca-image`: Rust без
   `unsafe` и без C, внутри того же одноразового Wasm-гостя без импортов, что и остальной
   разбор. Зависимости: только `miniz_oxide` (уже в проекте). `BitmapFactory`,
   `ImageDecoder`, `Glide` и т. п. байтов документа **не видят никогда**.
2. **Хост получает только канонический растр.** Результат — сырой RGBA 8 бит с заголовком
   (ширина, высота, флаги, длина). Хост проверяет заголовок и длину
   (`длина == ширина × высота × 4`, размеры в пределах лимита) и сам собирает `Bitmap` из
   массива пикселей. Гость считается взломанным: растр — просто числа.
3. **Всё ограничено.** Размер входа, число пикселей, память (растр уменьшается «на лету» до
   2048 px по длинной стороне, потолок строк в памяти), топливо процессора, дедлайн. Бомбы
   сжатия (PNG 1×1 → 60 000×60 000, GIF/JPEG с огромными размерами) отклоняются по
   заголовку, до выделения памяти.
4. **Ноль кликов.** Картинка внутри документа не раскодируется, пока человек не нажал
   «Показать картинку» (настройка «Показывать картинки сразу» выключена по умолчанию).
   Удалённые картинки (`external`) никогда не загружаются.
5. **Метаданные не показываются, но о них говорится.** EXIF, GPS, ICC-профиль, XMP,
   комментарии, миниатюра, данные после конца картинки — отбрасываются при показе и
   перечисляются в «Рентгене» (GPS в фото и неотрезанная миниатюра — классические утечки).
6. **Честность.** Анимация — только первый кадр (и об этом сказано); цветовой профиль не
   применяется; картинка уменьшена — указан исходный размер. Не поддерживаемые кодеки
   (JPEG 2000, JBIG2, CCITT, EMF/WMF, SVG, HEIC/AVIF) названы прямо, а не «не открылось».
   SVG — это XML со скриптами и ссылками: он **никогда** не раскодируется как картинка.

## 2. Модель угроз для картинок

| угроза | защита |
|---|---|
| порча памяти в декодере | безопасный Rust, запрет `unsafe`, `get()` вместо индексов, проверяемая арифметика; всё внутри Wasm |
| бомба распаковки / огромные размеры | проверка заголовка: ширина, высота, площадь, глубина; потолок буферов; топливо и дедлайн |
| эксплойт системного декодера Android | системный декодер не используется; в `Bitmap` попадает массив пикселей, который построил наш код |
| «картинка-полиглот» (ZIP/PDF/скрипт после конца картинки) | данные после конца картинки находятся и сообщаются; они не показываются |
| скрытая нагрузка «ни во что не входящими» байтами: приватные чанки PNG и маркеры JPEG, тело IEND, хвост zlib/LZW после конца потока, неизвестные расширения GIF, зазоры и заполнение строк BMP, лишние байты в заголовках JFIF/Adobe | декодер ведёт учёт байт: всё, что не картинка, не структура формата и не распознанные метаданные, считается в `unaccounted` и показывается в «Рентгене» (не бывает «молчаливых» блоков) |
| утечка приватности (GPS, модель камеры, серийные номера, автор, миниатюра) | сообщаются в «Рентгене», при показе и в стерильной копии отбрасываются; читаются все IFD-записи и все блоки EXIF файла |
| трекинг удалённой картинкой | картинки по ссылке не загружаются (уже так для документов) |
| скрытая вредоносная нагрузка в метаданных | метаданные не передаются в интерфейс, только счётчики и краткие факты |
| подмена типа (расширение `.png`, внутри JPEG или ZIP) | формат определяется по содержимому; расхождение с расширением сообщается |
| анимация как канал, мерцание | показывается один кадр |
| давление на память приложения | растр до 2048 px по длинной стороне; хост проверяет заявленную длину |

## 3. Архитектура

```text
 документ ──► arca-preview: находит картинку, даёт ей номер (id), «заглушка» в просмотре
                   │
 тап «Показать» ──► Op::Image(id) ──► Wasm-гость: достаёт байты картинки (resolver)
                                          └─► arca-image: определяет формат, проверяет лимиты,
                                              декодирует, уменьшает, поворачивает по EXIF
                   ◄── ImageModel {ширина, высота, RGBA, факты} ◄──┘
 хост (arca-engine): декодер с лимитами, проверка длины ──► JNI ──► Java: Bitmap из int[]
```

* `arca-image` — форматы PNG, JPEG (baseline и progressive), GIF, BMP (WebP и TIFF — только в планах);
  `sniff`, лимиты, уменьшение, EXIF (поворот и сводка приватности).
* ABI v5: операция `Image`, поле `flags` — идентификатор картинки (смысл зависит от формата
  документа и задаётся самим гостем), тип результата `Image`.
* Картинка, которую не удалось получить (повреждена, за лимитом, нет такого номера), —
  отказ этой операции (`OPERATION_FAILED`), а не «документ отклонён»: документ и другие его
  картинки по-прежнему открываются. Формат, который не читается, — `UNSUPPORTED_FORMAT`.
* Чего учёт байт не видит: содержимое энтропийных данных JPEG и самих пикселей (стеганография в
  младших битах) — то, что выглядит как картинка, считается картинкой (см. раздел 6).
* Идентификаторы: OOXML/ODF — номер файла среди картинок контейнера (`word/media/*`,
  `ppt/media/*`, `Pictures/*`); PDF — номер объекта XObject; RTF — номер `\pict` по
  порядку; отдельный файл-картинка — 0.
* Android: заглушка с типом, размерами и кнопкой; экран картинки с масштабированием
  (`PinchFrame`); картинки на страницах PDF; настройка автопоказа.

## 4. Этапы

1. `arca-image`: PNG, JPEG, GIF, BMP, EXIF, лимиты, уменьшение, тесты и мутационный фаззинг.
2. ABI v5, `Op::Image`, отдельные файлы-картинки (определение формата, «Рентген», просмотр).
3. Картинки внутри DOCX/PPTX/XLSX/ODF/RTF.
4. Картинки в PDF (JPEG и растровые потоки), на страницах и в тексте.
5. Движок, JNI, экраны Android, настройка.
6. Стерильная копия картинки (пересборка в чистый PNG, раздел 6), эмулятор, релиз.

Дальше (не в первом выпуске): WebP, TIFF, DOC/PPT (BLIP), EMF/WMF-подмножество,
постраничная плитка для очень больших картинок.

## 5. Лимиты по умолчанию

| лимит | значение |
|---|---|
| размер картинки на входе | 64 МиБ |
| сторона | до 30 000 px |
| площадь для потокового декодирования | до 64 Мпкс |
| площадь, если нужен весь растр (прогрессивный JPEG, чересстрочный PNG/GIF, RLE в BMP) | до 16 Мпкс |
| проходов (scan) в JPEG | до 200; суммарно блоков по всем проходам — не больше 32 × блоков картинки |
| кадр GIF (первый) | проверяется сам по себе: сторона и площадь в тех же пределах, что и холст |
| «Рентген» дочитывает данные картинки до конца потока (zlib в PNG, LZW в GIF) | если распакованный размер до 64 МиБ (PNG) / кадр до 32 Мпкс (GIF); крупнее — при показе |
| выход при просмотре | до 2048 px по длинной стороне (RGBA, до 16 МиБ) |
| стерильная копия | до 4 Мпкс (с опцией «полный размер» — до 16 Мпкс), целым коэффициентом уменьшения |
| кадров в GIF | читается первый |

## 6. Стерильная копия картинки

Для файла-картинки (PNG, JPEG, GIF, BMP) «стерильная копия» — это **новый файл**, а не оригинал
с вырезанными кусками. Песочница декодирует картинку (`arca-image`, как для просмотра, но без
уменьшения до экранного размера), а затем **пишет PNG заново** (`arca_image::encode_png`):
сигнатура, `IHDR`, данные пикселей, `IEND` — больше ничего. Ни профиля, ни текстовых чанков, ни
EXIF, ни миниатюры, ни остальных кадров анимации, ни байтов после конца картинки, ни устройства
исходного файла в копии нет. Структура оригинала (то, на чём играют эксплойты и полиглоты) не
доходит до системного декодера, который откроет копию.

Что делается по дороге:

* размер: картинка больше **4 Мпкс** (опция «Сохранить полный размер» — **16 Мпкс**) уменьшается
  целым коэффициентом, и копия говорит об этом («pixels: reduced from … to …»): песочница
  интерпретирует каждый шаг декодирования и записи, цена растёт с числом пикселей;
* поворот по EXIF применяется к пикселям (в копии нет EXIF, который бы его потерял);
* цвет **полностью прозрачных пикселей обнуляется** (в них прячут данные; видимого эффекта нет);
* тип PNG подбирается точно: серый, серый с прозрачностью, RGB или RGBA, 8 бит; для каждой строки
  выбирается лучший из пяти фильтров PNG;
* копия **читается обратно** тем же декодером в строгом режиме (`decode_sterile`: проверены CRC всех
  чанков и Adler-32 потока zlib; в файле нет повреждений, байтов после конца, метаданных,
  необъяснённых байтов, анимации) и сверяется с пикселями по отпечатку SHA-256 (картинка и копия не
  лежат в памяти одновременно); затем копия проходит обычную проверку «Рентгеном».

Что копия честно **не** сохраняет: цветовой профиль (цвета считаются sRGB; об этом сказано в
списке изменений), анимацию (только первый кадр), CMYK (преобразуется приближённо). Фотография в PNG
больше, чем в JPEG (без потерь, но без JPEG-сжатия). Чего копия **не может** убрать: скрытое в самих
видимых пикселях (стеганография в младших битах) — пересохранение пикселей этого не меняет.

Измерено в песочнице (ноутбук; на телефоне интерпретатор медленнее в несколько раз): JPEG
4000×3000 → PNG 3 Мпкс — около 24 млрд единиц топлива, 14 с; полный размер 12 Мпкс — около 88–105
млрд, около 55 с. Бюджет топлива и времени выдаёт хост только файлу, который по первым байтам является
картинкой (`Engine::size_for_picture_copy`); флаг запроса `FULL_SIZE` (ABI v5) выбирает размер.
