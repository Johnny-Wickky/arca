# Как выпустить версию

Релиз Android-приложения собирает, подписывает, проверяет и публикует GitHub Actions
(`.github/workflows/android.yml`) при появлении тега `v*`. Для публикации релиза разработчик готовит
атрибуцию и ключ (один раз), пишет заметки релиза и ставит git-тег. Основной канал
распространения — подписанный APK в GitHub Releases (пре-релиз). Workflow `ios.yml` на тегах `v*`
собирает XCFramework и прогоняет тесты Swift на macOS-раннерах.

## Один раз перед первым релизом

### 1. Атрибуция создателей — без заглушек

Релизный контроль (`ARCA_RELEASE=1`) не даёт собрать приложение, пока в
`crates/arca-attribution/src/upstream.rs` остались домены-заглушки `arca.invalid`. Это
сделано намеренно: экран «О приложении» — то, на чём держится проект и условия лицензии.

Нужно заменить значения на настоящие (ссылки на донаты необязательны):

| константа | что вписать |
|---|---|
| `UPSTREAM_HOMEPAGE` | страница проекта (например, `https://github.com/Johnny-Wickky/arca`) |
| `UPSTREAM_SOURCE` | где опубликован исходный код (обязательство AGPLv3 §13), обычно тот же репозиторий |
| `UPSTREAM_AUTHORS[0]` | имя создателей и ссылка на них |
| `UPSTREAM_DONATION_LINKS` | необязательно: пусто, пока ссылок нет; добавьте, когда появятся |

Затем обновить закреплённый отпечаток — сборка сама покажет нужное значение:

```sh
cargo build -p arca-attribution            # остановится и напечатает computed: <64 hex>
echo '<computed>' > crates/arca-attribution/UPSTREAM_FINGERPRINT
ARCA_RELEASE=1 cargo build -p arca-attribution --release   # должно собраться
cargo test -p arca-attribution
```

Менять отпечаток вправе только оригинальные создатели и только когда они сами правят свои записи;
форки добавляют свои данные в `fork_attribution.toml`, а не меняют оригинальные.

### 2. Ключ подписи

Приложение, подписанное другим ключом, **нельзя обновить поверх** установленного. Поэтому ключ
создаётся один раз, хранится в двух надёжных местах вне репозитория и никогда не меняется без
крайней необходимости.

```sh
keytool -genkeypair -keystore arca-release.p12 -storetype PKCS12 -alias arca \
    -keyalg RSA -keysize 4096 -validity 36500 -dname "CN=Arca, O=Arca"
base64 -w0 arca-release.p12 > arca-release.p12.b64      # macOS: base64 -i … -o …
```

Секреты принадлежат **окружению `release`**, а не репозиторию: *Settings → Environments → release →
Environment secrets*. Окружение создайте заранее (имя в workflow — ровно `release`).

| секрет окружения `release` | значение |
|---|---|
| `ARCA_KEYSTORE_B64` | содержимое `arca-release.p12.b64` |
| `ARCA_KEYSTORE_PASS` | пароль хранилища |
| `ARCA_KEY_ALIAS` | `arca` |
| `ARCA_KEY_PASS` | пароль ключа (если не задан — равен паролю хранилища) |

Почему окружение. Секреты видит единственное задание `package-release` (оно запускается только для тегов
`v*` и объявляет `environment: release`); оно передаёт их шагам через `env:` этих шагов, а не через
`GITHUB_ENV`, и в конце удаляет файл ключа с раннера. Сборки pull request, веток и ручные запуски
(`package`) секретов не видят вовсе и подписываются одноразовым ключом, созданным на время сборки. В настройках
окружения рекомендуется включить обязательных проверяющих и ограничить развёртывание тегами `v*`
(*Deployment branches and tags*): это настраивается в параметрах репозитория.

Если в окружении `release` ключа нет (или он задан частично), тег всё равно соберётся, но пакет будет подписан
**одноразовым ключом**, а заметки релиза начнутся с предупреждения об этом. Такой пакет работает, но его
придётся удалить перед установкой версии с постоянным ключом. Для первой пробной версии это допустимо, для
стабильных — нет. Ключ в каталоге `signing/` на машине разработчика (он перечислен в `.gitignore`) в CI не
участвует: коммитить его нельзя, а локальные сборки им подписывать не нужно.

Отпечаток сертификата подписи автоматически попадает в заметки релиза: сохраните его и
сверяйте с ним все следующие версии.

**Постоянный ключ 0.3.0 (ручная подпись).** Ключ `PKCS12 RSA-4096` лежит вне репозитория:
`../arca-keys/arca-release.p12` (рядом с каталогом проекта), алиас `arca`, срок 100 лет, пароль хранится только у
владельца ключа и не попадает в Git, логи сборки и скрипты. Отпечаток сертификата (SHA-256):
`3b3b819dea6a02ffdea05ac7ce53df9b2bdf004dac3082c048557383cfaf737e`. Сборка и подпись вручную (Linux или контейнер
с Rust 1.97, NDK 27.3 и build-tools 36):

```sh
export ARCA_RELEASE=1 ARCA_KEYSTORE=../arca-keys/arca-release.p12 ARCA_KEY_ALIAS=arca
read -rs ARCA_KEYSTORE_PASS && export ARCA_KEYSTORE_PASS   # пароль вводится, а не записывается
bash tools/android/build-local.sh                           # гость -> библиотеки -> dist/arca-0.3.0.apk
apksigner verify --verbose --print-certs dist/arca-0.3.0.apk
```

Файлы ключей (`.p12`, `.pfx`, `.jks`, `.keystore`, `.key`, `.pem`) запрещены в репозитории:
`tools/check-unsafe.sh` (он выполняется в CI) падает, если такой файл отслеживается Git, а
`tools/hooks/pre-commit` (`git config core.hooksPath tools/hooks`) не даёт его закоммитить.
Сборки `0.2.x` подписаны одноразовыми ключами, поэтому переход на 0.3.0 требует **чистой установки**
(сначала удалить старый APK).

## Каждый релиз

1. Напишите `docs/releases/vX.Y.Z.md` — заметки релиза. Воркфлоу откажется публиковать без
   этого файла. Они должны честно говорить, что проверено, а что нет (см. `v0.1.0.md`, `v0.2.2.md`);
   если заметки прежней версии оказались неверными, исправление кладут и в её файл, и в новые заметки.
2. Обновите версию: `version` в корневом `Cargo.toml` и `versionName`/`versionCode` в
   `android/app/src/main/AndroidManifest.xml` — для локальных сборок и чтобы файлы не расходились
   с тегом; в релизе версия пакета берётся из тега.
3. Убедитесь, что `main` зелёный: `ci` и `android` (job `checks`). Локально перед тегом полезно прогнать
   `cargo test --workspace`, `bash tools/check-unsafe.sh`, `bash tools/check-lockfile.sh` и
   `bash tools/check-reproducible.sh` (см. «Локальная сборка в WSL» ниже).
4. Поставьте и отправьте тег:

   ```sh
   git tag -a v0.1.0 -m "Arca 0.1.0"
   git push origin v0.1.0
   ```

   В GitHub Desktop: *History → правый клик по коммиту → Create Tag…*, затем *Push origin*.
5. Следите за запуском *Actions → android*:

   | job | что делает |
   |---|---|
   | `checks` | проверки приложения и ресурсов, JNI-тесты на JVM, контрактные тесты с настоящим гостем |
   | `package` | не для тегов: гость Wasm → три нативные библиотеки (проверка выравнивания 16 КиБ) → APK с одноразовым ключом → проверка пакета; секретов не видит |
   | `package-release` | только для тегов `v*`, окружение `release`: то же плюс релизный контроль атрибуции (`ARCA_RELEASE=1`), разбор тега, подпись релизным ключом (или одноразовым, если ключа нет) |
   | `release` | создаёт GitHub Release (помечен как pre-release), прикладывает APK, контрольную сумму, отчёт о проверке пакета и хэши библиотек и гостя; если пакет подписан одноразовым ключом, заметки начинаются с предупреждения |
   | `emulators` | прогон на эмуляторах Android 8–16 с разными формами окна; не блокирует релиз, результаты и снимки экранов — в артефактах |

6. После публикации: скачайте APK из Releases и сверьте SHA-256 с указанным в заметках;
   `apksigner verify --print-certs arca-X.Y.Z.apk` должен показать сохранённый отпечаток.

## Версии

* Тег `vMAJOR.MINOR.PATCH[-суффикс]`, каждая часть — число (MINOR и PATCH не больше 999); иначе
  `package-release` останавливается. `versionName` — это тег без `v`.
* `versionCode` = `MAJOR·1 000 000 + MINOR·1 000 + PATCH` (суффикс не учитывается), поэтому
  `v0.1.0` → 1000, `v0.2.0` → 2000, `v0.2.2` → 2002, `v1.0.0` → 1 000 000. Он только растёт; Android не
  позволит установить меньшее значение поверх большего.
* Схема до 1.0: `0.MINOR.PATCH`. Серия `0.2.x` — раунд проверки и исправлений поверх 0.2.0: PATCH растёт
  для исправлений и выпусков без новых форматов, MINOR — для новых возможностей. Тега `v0.2.1` нет;
  после неработающего `v0.2.0` следующей версией выбрана `0.2.2`.
* Теги не переиспользуются. Неудачный релиз удаляется (Release и тег), версия поднимается. Тег `v0.2.0`
  указывает на коммит, который не собирался (заметки к нему исправлены в `docs/releases/v0.2.0.md`);
  его не переписывали, исправление вышло под новым номером.

## Если что-то пошло не так

| симптом | причина и что делать |
|---|---|
| `package` падает на «release gate» | остались заглушки в атрибуции — раздел «Один раз… 1» |
| `release` падает: «missing docs/releases/…» | нет файла заметок для тега |
| `ARCA_KEYSTORE…` ошибки подписи | секреты окружения `release` заданы частично или пароль неверный; удалите все или исправьте |
| `package-release` ждёт и не стартует | у окружения `release` включены обязательные проверяющие — одобрите запуск в *Actions* |
| пакет подписан «одноразовым ключом» на теге | в окружении `release` нет полного набора секретов (секреты репозитория для этого задания не используются) |
| `checks` падает в `host-test` | настоящая ошибка: в логе — какой документ и какая проверка; чинить код, а не тест |
| `emulators` красные при зелёных остальных | смотрите артефакты `emulator-api-NN`: `report.txt`, `logcat.txt`, снимки экранов. На релиз не влияет, но падение приложения — повод для патча |

## Локальная сборка в WSL (Ubuntu) или на Linux

Rust-часть не требует ничего, кроме линкера: C и C++ не собираются. Работайте в каталоге внутри Linux
(`~/arca`), а не в `/mnt/c/...`. Шаги соответствуют скриптам автоматической сборки в CI:

```sh
sudo apt install build-essential zip unzip curl git openjdk-17-jdk-headless
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh      # затем перезапустить оболочку
cd ~/arca && rustup toolchain install                              # 1.97.0, wasm32 и цели Android — из rust-toolchain.toml

cargo test --workspace --locked                                    # проверки ядра
bash tools/build-guest.sh                                          # Wasm-гость; печатает SHA-256, проверяет «ноль импортов»
bash tools/check-unsafe.sh && bash tools/check-lockfile.sh
bash tools/check-reproducible.sh                                   # гость и libarca_jni.so из двух каталогов дают один хэш
```

APK локально (Android SDK `platforms;android-36`, `build-tools;36.0.0` и NDK ради линкера
ставятся `sdkmanager`; переменные линкера и флаги выравнивания 16 КиБ — те же, что в шаге *native libraries*
в `.github/workflows/android.yml`):

```sh
export ARCA_GUEST_WASM=$PWD/target/wasm32-unknown-unknown/guest/arca_guest_xray.wasm
# для каждой цели aarch64-linux-android, armv7-linux-androideabi, x86_64-linux-android:
#   cargo build --release --locked -p arca-jni --target <цель>   → положить в native/<abi>/libarca_jni.so
ANDROID_HOME=... ARCA_NATIVE_DIR=$PWD/native ARCA_THROWAWAY_KEY=1 bash tools/android/build-apk.sh
```

Такой пакет подписан одноразовым ключом и годится для проверки, а не для выпуска: релиз собирает CI из тега.
Не кладите релизный ключ на машину разработчика ради сборки. Клиент iOS (`tools/ios/*`) на Linux не собирается.

## Воспроизводимость

Сборка использует закреплённые версии: Rust 1.97.0 (`rust-toolchain.toml`), `Cargo.lock` с
`--locked`, `build-tools;36.0.0`, образ `ubuntu-24.04`, действия по SHA. Пути вырезаются из
бинарных файлов (`--remap-path-prefix`). Побитовая воспроизводимость APK **не заявляется**.
Что измерено на дереве 0.2.4 (WSL, два каталога с разными именами, `tools/android/build-local.sh`
в каждом): три `libarca_jni.so` и все записи APK, кроме `META-INF/`, совпали байт в байт; сам
файл APK различается подписью (одноразовый ключ). Что проверяется в CI: Wasm-гость и хостовая
`libarca_jni.so` собираются одинаково из разных каталогов (`tools/check-reproducible.sh`, задание
`reproducible`), а гость — ещё и в двух разных дистрибутивах (задание `reproducible-guest`:
`ubuntu:22.04` и `debian:bookworm`, свой rustup, `--locked`, `--remap-path-prefix`,
`SOURCE_DATE_EPOCH`, разные каталоги сборки; различие SHA-256 проваливает задание). Тот же хэш
(`6fb4064a…`) получился при локальной проверке в Docker в обоих образах и в WSL. Оговорка: без
`--remap-path-prefix` в модуль попадают пути исходников зависимостей из `CARGO_HOME`, и хэш гостя
зависит от них (`tools/build-guest.sh` флагов не добавляет: тот же коммит даёт `664aa861…`); поэтому
хэши сравнивают между сборками с одинаковыми флагами. Хэш Wasm-гостя (он печатается в журнале
сборки, в «Диагностике» приложения и в заметках релиза) — то, что можно сравнивать между сборками
одного коммита.
