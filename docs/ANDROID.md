# Arca для Android

Приложение, которое открывает Word, Excel, PowerPoint, OpenDocument, RTF, PDF и письма
Outlook так, как будто файл — враждебный: сначала «рентген безопасности», потом
просмотр текста и таблиц, который собирает **Rust-ядро внутри одноразовой
WebAssembly-песочницы**. Приложение ничего не исполняет из документа, не имеет сети и
не просит никаких разрешений (манифест пуст, см. §4).

Этот файл — справочник по Android-части: что поддерживается, как устроено, как собрать
и что проверено, а что — нет. Общая архитектура — [`ARCHITECTURE.md`](ARCHITECTURE.md),
модель угроз — [`SECURITY_THREAT_MODEL.md`](SECURITY_THREAT_MODEL.md), выпуск релиза —
[`RELEASING.md`](RELEASING.md).

## 1. Устройство

```text
 Java-приложение (org.arca.viewer, только классы Android Framework)
   │  JNI: статические native-методы, дескрипторы файлов, JSON страницами
   ▼
 libarca_jni.so  ── arca-jni ── arca-engine ── arca-sandbox (wasmi)
                                                    │  0 импортов
                                                    ▼
                                      Wasm-гость: рентген · стерилизатор · просмотр
```

* **Нативный код — одна библиотека** `libarca_jni.so` (Rust, без C/C++). Wasm-гость вшит в неё
  (`include_bytes!`), его SHA-256 записан при сборке и виден в «О приложении» и в
  «Диагностике». Единственный файл с `unsafe` — `crates/arca-jni/src/ffi.rs`, весь JNI-слой
  проверяется `tools/check-unsafe.sh` и тестами на настоящей JVM с `-Xcheck:jni`.
* **Документ не попадает в кучу Java.** Файл читается из `ParcelFileDescriptor` прямо в память
  ядра; в Java возвращаются только маленькие JSON-страницы результата (по 64 элемента).
  Дескрипторы и результаты — числа-счётчики, а не указатели.
* **Интерфейс — программный** (без XML-разметки экранов), один `Activity`, без AndroidX, без
  Gradle и без сторонних Java-библиотек. Это сознательный выбор: у приложения для просмотра
  враждебных файлов цепочка поставок Java-стороны должна быть пустой, а каждую строку, что
  попадёт в APK, можно прочитать в этом репозитории. Цена — больше ручного кода, чем с
  Jetpack; она описана в §7.
* **Нет Flutter на Android.** План Фазы 4 предусматривал Flutter; для Android он заменён
  описанным выше нативным приложением (меньше кода и зависимостей в доверенной базе,
  прямой доступ к `ParcelFileDescriptor`). Клиент iOS (`app/`, `crates/arca-ffi`) — отдельный
  нативный клиент на Swift (см. [`ARCHITECTURE.md`](ARCHITECTURE.md) §4.10).

### Что умеет приложение

* **Открытие:** из любого файлового менеджера и мессенджера («Открыть с помощью»,
  `content://`), системным выбором файла и перетаскиванием; 31 расширение
  и распознавание формата по содержимому, а не по имени.
* **Рентген безопасности** (вердикты `Чисто` / `Скрытые трекеры` / `Активное содержимое` /
  `Не проверено` / `Отклонён`): макросы VBA и XLM, DDE, OLE/ActiveX, эксплойты, внешние
  ссылки и шаблоны, трекеры, скрытое содержимое, метаданные, атаки на формат.
* **Просмотр:** DOCX/DOCM/DOTX/DOTM, DOC; XLSX/XLSM/XLTX/XLTM/XLAM, XLS; PPTX/PPTM/PPSX/PPSM/POTX/POTM,
  PPT; ODT/ODS/ODP; RTF; PDF (текст); Visio VSDX (текст фигур, данные, ссылки и соединения) и VSD (только
  текст фигур: соединители, данные, гиперссылки и мастера не читаются, об этом сказано в уведомлении);
  базы Access (таблицы; запросы — как сохранённые строки, для простого `SELECT` ещё и приближённый SQL с
  пометкой «не проверено»); MSG (письма Outlook); TXT/CSV/TSV/Markdown. Строки, которые вставил сам
  просмотр (подпись соединения, имя фигуры без текста, SQL), отличаются от текста документа.
  Подробности и ограничения — в заметках релиза и [модели угроз](SECURITY_THREAT_MODEL.md).
* **Картинки:** файлы PNG/JPEG/GIF/BMP и картинки внутри документов (DOCX/PPTX/XLSX, ODF, RTF, PDF)
  раскодирует песочница, а не системный декодер; в документе картинка — заглушка с размером, по тапу она
  открывается на весь экран (щипок, двойной тап); на странице PDF по тапу открывается картинка под пальцем.
  Настройка «Показывать картинки сразу» выключена по умолчанию. Метаданные картинки (GPS, камера, миниатюра)
  показываются отдельным списком, а не передаются в интерфейс.
* **Постраничный вид (PDF, слайды, листы, схемы Visio, схема связей Access):** страница рисуется из примитивов, которые отдаёт песочница; картинки — серые
  прямоугольники (по тапу открываются), шрифты заменены. Листание — стрелками.
* **В просмотре:** поиск по документу (с подсветкой и переходом), оглавление и закладки,
  масштаб (щипок и кнопки; запоминается), гиперссылки ячеек таблиц.
* **Стерильная копия** (OOXML, Visio OOXML, OpenDocument, PDF, DOC/XLS/PPT/RTF → новый
  .docx/.xlsx/.pptx, картинка → новый PNG, написанный из пикселей; до 4 Мпкс, «Сохранить полный размер» — до 16): без макросов, внешних связей, ревизий, комментариев и метаданных; результат
  проверяется рентгеном заново; сохранение через системный диалог (без доступа к хранилищу).
* **Отчёт** можно скопировать или отправить как текст; хэш SHA-256 копируется.
* **Настройки:** тема (системная/светлая/тёмная), язык (системный/русский/английский),
  размер текста просмотра, «блокировать снимки экрана» (включено по умолчанию), «показывать
  скрытое по умолчанию» (выключено).
* **Диагностика:** версия ядра, хэш гостя, лимиты устройства, самотест всего конвейера на
  встроенном документе.
* **О приложении:** создатели оригинального ядра и их ссылки на поддержку, карточка форка
  (если есть) — всегда рядом, а не вместо; лицензии и сторонние компоненты.

## 2. Поддерживаемые версии Android

`minSdk 26` (Android 8.0) … `targetSdk 36` (Android 16). Всё, что новее API 26, изолировано в
`ui/Compat.java` за проверками `SDK_INT`; `tools/android/check-android.sh` компилирует
приложение против `android.jar` API 26 и API 36 и падает, если вызов новее 26 найден вне
`Compat`.

| Android | API | Что учтено |
|---|---|---|
| 8.0, 8.1 | 26, 27 | нижняя граница: светлая/тёмная тема приложением, навигационная панель, обычный «Назад» |
| 9 | 28 | вырез экрана (`displayCutout`, режим коротких краёв), заголовки для TalkBack |
| 10 | 29 | отключение системной «подложки» панелей, жестовая навигация, системная тёмная тема |
| 11 | 30 | `WindowInsetsController`: экран под системными панелями, отступы по реальным вставкам |
| 12, 12L | 31, 32 | без особых веток; окно изменяемого размера (12L: большие экраны, панель задач) |
| 13 | 33 | предиктивный жест «Назад», язык приложения (`localeConfig`), без снимка в «Недавних» |
| 14, 15 | 34, 35 | без особых веток; режим «от края до края» в приложении включён с самого начала; страницы памяти 16 КиБ (§4) |
| 16 | 36 | цель сборки; окно изменяемого размера, ориентация не фиксируется — ограничения Android 16 на больших экранах не затрагивают приложение |

Ветки по API 31, 32, 34, 35 в коде отсутствуют намеренно; это значит «не требуется», а не
«проверено на устройстве». Что проверено на устройствах и чем — см. §6.

### Архитектуры процессора

| ABI | Что это | Состояние |
|---|---|---|
| `arm64-v8a` | почти все телефоны и планшеты после 2016 | собирается и проверяется на выравнивание; основная цель |
| `armeabi-v7a` | 32-битные телефоны, старые Android Go, часть планшетов | собирается; **не запускалась** (нет устройства/эмулятора в CI) |
| `x86_64` | эмуляторы, Chromebook, часть Intel-планшетов | собирается и **запускается** на эмуляторах CI (API 26–36) |
| `x86` (32-бит) | практически исчез | не собирается |

Нативные библиотеки собираются с выравниванием сегментов по 16 КиБ (`-Wl,-z,max-page-size=16384`)
и хранятся в APK без сжатия, выровненными по 16 КиБ (`zipalign -P 16`,
`android:extractNativeLibs="false"`): устройства Android 15+ со страницами 16 КиБ загружают такую
библиотеку, а Google Play принимает такой пакет. `arca-devtools elf-check` (`crates/arca-devtools`) проверяет
выравнивание каждого `PT_LOAD` в CI.

## 3. Экраны: телефоны, планшеты, складные и раскладные

Раскладка считается **по окну, а не по устройству**: `screenWidthDp`/`screenHeightDp` меняются
при складывании и раскладывании, разделении экрана, оконном режиме и повороте. Поэтому
устройству не нужно «быть известным»: любое новое — это просто окно другого размера.

| Класс окна | Ширина | Что происходит |
|---|---|---|
| компактный | < 600 dp | одна колонка; поля 12 dp (при ширине < 360 dp) или 16 dp |
| средний | 600–839 dp | одна колонка шириной до 720 dp по центру; поля 24 dp |
| расширенный | ≥ 840 dp | **две панели** (сводка/действия слева 320–420 dp, содержимое справа); поля 32 dp |
| низкое окно | высота < 480 dp | компактные отступы и заголовки (ландшафт телефона, «раскладушка» в палатке, обложка Flip) |

Пороги — в `core/Breakpoints.java`, это чистые функции, их проверяет `android/core-test`
(в том числе граничные значения 599/600/839/840 dp и очень узкие/низкие окна).

Что делает приложение при смене формы окна:

* `android:resizeableActivity="true"`, ориентация не фиксируется, `supports_size_changes`;
* `Activity` сам обрабатывает `orientation|screenSize|smallestScreenSize|screenLayout|density|`
  `keyboard|keyboardHidden|navigation|colorMode|layoutDirection|touchscreen` — не пересоздаётся,
  а перестраивает вид; **сканирование не перезапускается**, прокрутка и открытый документ
  сохраняются: сессия живёт дольше `Activity`;
* тема и язык пересоздают `Activity`, чтобы подгрузились нужные ресурсы;
* отступы берутся из реальных вставок (системные панели и вырезы: камера, шарнир, скругления);
* крупный шрифт (`font_scale` до 2,0), RTL (`supportsRtl`) и тёмная тема проверяются
  прогоном на эмуляторах (§6).

Типовые сценарии:

| Устройство / режим | Размеры окна, dp (пример) | Как показывается |
|---|---|---|
| Galaxy Z Fold, внешний экран | ≈ 344 × 880 | компактный |
| Galaxy Z Fold, внутренний экран | ≈ 690 × 830 | средний, колонка до 720 dp |
| Pixel Fold, внутренний экран | ≈ 840 × 700 | расширенный (две панели) |
| Galaxy Z Flip / Tecno Phantom V Flip, основной экран | ≈ 400 × 980 | компактный |
| Flip, обложка | ≈ 384 × 400 | компактный, низкое окно |
| Планшет 10–11″, портрет / ландшафт | ≈ 800 × 1280 / 1280 × 800 | средний / расширенный |
| Телефон в разделённом экране | ≈ 411 × 460 | компактный |
| Окно на Chromebook / в режиме рабочего стола | любое | по ширине окна |

Это размеры, на которых работает вёрстка и прогоняется эмулятор; точные значения у конкретных
моделей и режимов зависят от прошивки и плотности.

### Складные устройства: сгиб, шарнир и поза

Приложение живёт без AndroidX, поэтому Jetpack WindowManager (`FoldingFeature`) недоступен, а
рефлексия по `androidx.window.extensions` запрещена политикой проекта. Остаются только публичные
API платформы; что в них есть на самом деле (проверено по `android.jar` API 36 и `api-versions.xml`):

| API | С какого уровня | Что даёт | Используется |
|---|---|---|---|
| `Sensor.TYPE_HINGE_ANGLE` | 30 | угол шарнира, но не положение сгиба | да: определяет, приоткрыто ли устройство |
| `WindowInsets.getDisplayCutout().getBoundingRects()` | 28 | прямоугольники вырезов в координатах окна; двухэкранные устройства (класс Surface Duo) отдают шарнир как вырез | да: единственный источник точного прямоугольника |
| `WindowManager.getCurrentWindowMetrics()`, `getMaximumWindowMetrics()` | 30 | точный размер окна и дисплея в пикселях | да (до 30 — размер из `Configuration` и `getRealMetrics`) |
| `WindowInsets.getBoundingRects(int)` | 35 | то же, что выше, по типам вставок | нет: не даёт ничего нового |
| `android.hardware.devicestate.DeviceStateManager` | нет в публичном SDK | состояние устройства (сложено, открыто, «книжка») | нет: класса нет в `android.jar` (системный API) |
| `Configuration.screenLayout`, `smallestScreenWidthDp` | 1 / 13 | размер и форма окна, но не сгиб | уже используются для классов размера |

Итог: положение сгиба **гибкого** экрана (Galaxy Z Fold, Pixel Fold, Flip) публичный API не сообщает;
оно по-прежнему выводится из формы дисплея (`core/Posture`). Точный прямоугольник известен только
если система передала шарнир как вырез.

**Модель** (чистая Java, без Android, `core/Fold` и `core/FoldLayout`, проверяется на JVM):

* `Fold` — сгиб: направление (вертикальный или горизонтальный), полоса `start..end` в dp в координатах
  окна, признак *закрывающего* (шарнир-вырез скрывает пиксели) и *разделяющего* (окно делится на две
  области). Закрывающий сгиб всегда разделяющий; незакрывающий (гибкий экран) разделяет только пока
  устройство приоткрыто (датчик угла) и не плоское.
* `Fold.fromRectsPx` отличает шарнир от камеры и выреза у края: прямоугольник должен идти почти через всё
  окно (не меньше 90 %), быть не толще трети окна и лежать не ближе 15 % к краю. Пиксели переводятся
  в dp «наружу», чтобы округление не уменьшало шарнир. Платформа важнее догадки.
* `FoldLayout.compute` даёт области `{left, top, width, height}` в dp: *основную* (документ) и
  *вспомогательную* (элементы управления). Ни одна область не подходит к сгибу ближе половины
  зазора (`Posture.GAP_DP / 2 = 12` dp с каждой стороны), поэтому строка текста не окажется под
  шарниром и не пересечёт сгиб.
  * **Книга** (вертикальный сгиб): документ на странице со стороны чтения (слева, справа при письме справа
    налево), управление на другой.
  * **На столе** (горизонтальный сгиб): документ на верхней половине, управление на нижней. Пропорции следуют
    за сгибом: при сгибе на 30 % высоты — 288 dp сверху и 688 dp снизу (окно 1000 dp).
  * Область уже 200 dp (`MIN_PANE_DP`) не используется: если сторона чтения уже, документ занимает широкую
    сторону, если вторая область уже — управление остаётся в документе. Окно, не пересекающее сгиб,
    плоское устройство и окно, целиком закрытое шарниром, остаются целыми.
  * Гибкий сгиб в окне короче 480 dp не делит окно (как раньше); шарнир, скрывающий пиксели, обходится
    при любом размере.

**Подключение.** `ui/Hinge` берёт прямоугольники вырезов из вставок окна (`MainActivity` перестраивает экран,
когда они изменились), угол шарнира с датчика, считает `FoldLayout` и сообщает его `MainActivity` и
`Adaptive`: экран строится в основной области, поэтому все размеры (`Adaptive.widthDp`, колонки, поля)
считаются по ней. Экраны могут вынести управление в отдельную область, переопределив `Screen.dock()`:
`PreviewScreen` переносит туда список разделов, `PagesScreen` — переключатель страниц. Остальные экраны
занимают основную область целиком, вторая остаётся пустой. Все новые вызовы платформы лежат в `ui/Compat`
(вложенные классы `Api28` и `Api30`, защищены `SDK_INT`); на API 26–27 ничего не меняется, на API 28–29
работает только путь через вырез, на API 30+ — и датчик. Экран «Диагностика» показывает строку
`fold: …` (поза и источник: `hinge cutout` или `hinge sensor`), чтобы на устройстве было видно, что
решило приложение.

**Что проверено.** Только логикой: тесты `fold` и `posture` в `android/core-test/CoreTest.java` (прямоугольники и
отсев камеры и выреза у края, вертикальные и горизонтальные сгибы, закрывающий шарнир, окно, не пересекающее
сгиб, пропорции «на столе», правая-налево, полный перебор размеров окна, положений и толщины сгиба
на предмет «колонка не подходит к сгибу»), и компиляция против `android.jar` API 26 и 36
(`tools/android/check-android.sh`). Физического складного устройства (и двухэкранного) у проекта нет;
сам прямоугольник шарнира в `WindowInsets` на конкретных прошивках не наблюдался. Допущения, которые
может поправить только устройство: что вырез-шарнир передаётся в окно приложения (режим выреза окна
`SHORT_EDGES` на длинной стороне может заставить систему сдвинуть само окно) и что его прямоугольник
в координатах окна, а не дисплея. Если это не так, приложение остаётся на датчике и форме экрана, как раньше.
Эмуляторный прогон (`tools/android/emulator-smoke.sh`) меняет размер окна, но не воспроизводит ни шарнир,
ни датчик угла: профили складных AVD там не используются, и поза «книга» или «на столе» им не проверяется.

### Что не сделано (и почему)

* **Точный сгиб гибкого экрана.** Его положение знает только `FoldingFeature` из Jetpack WindowManager
  (AndroidX), а приложение сознательно живёт без AndroidX, и рефлексия по `androidx.window.extensions`
  запрещена. Публичный API даёт угол шарнира, а прямоугольник — только для шарнира, переданного как
  вырез (см. выше). Поэтому у Z Fold, Pixel Fold и Flip сгиб по-прежнему выводится из формы экрана
  (посередине, вдоль длинной стороны у «книжек» и поперёк у «раскладушек») и учитывается только пока
  устройство приоткрыто, а окно занимает весь экран. Эвристика и вырез-шарнир покрыты модульными тестами; проверки на настоящем складном или
  двухэкранном устройстве в набор не входят. Если система не передаст шарнир вырезом (или передаст в
  другой системе координат) и датчика угла нет, окно — просто окно большого размера, и шарнир может
  закрыть часть текста. Помимо вырезов, учитываются обычные вставки выреза и системных панелей.
* **Внешний экран Galaxy Z Flip (обложка).** Сторонние приложения там открываются только если
  пользователь разрешил это в системе (настройки обложки/Labs); на самой обложке приложение
  ведёт себя как компактное низкое окно. Проверить это на устройстве без устройства нельзя.
* **Перетаскивание файла в окно** работает там, где система доставляет событие перетаскивания
  (многооконный режим, Chromebook, DeX); проверено только логикой, не на устройстве.

## 4. Безопасность самого приложения

* **Разрешений нет вообще.** Манифест не содержит ни одного `uses-permission` (ни `INTERNET`, ни
  `POST_NOTIFICATIONS`); системных уведомлений, будильников и приёмников тоже нет. Напоминание о
  поддержке разработчиков — карточка на главном экране приложения. Сборка проверяет это строго:
  `build-apk.sh` требует, чтобы в `aapt2 dump badging` не было ни одной строки `uses-permission*`, а
  `arca-devtools check-resources` разбирает манифест как XML и отвергает любой элемент
  `uses-permission*`/`permission`, а также `android:debuggable`, `allowBackup` не равный `false` и экспортируемый компонент
  вне списка (`.MainActivity`).
* **Локальная статистика.** Ядро (Rust, `arca_engine::stats`) считает по дням, что Arca сделала
  на этом устройстве: открыто документов, найдено чистых, обезврежено трекеров и активного
  содержимого, отклонено, проверено не полностью, стерильных копий, открытых картинок (кольцо из
  400 дневных корзин плюс итог «за всё время»; соответствие вердикта счётчикам описано в одном
  месте — в документации модуля). Приложение хранит только непрозрачный блоб
  (версия, CRC-32, жёсткие границы разбора) в `SharedPreferences`; имён файлов, содержимого и
  хэшей не хранится вообще. Номер дня даёт платформа (локальный календарь), часов в ядре нет.
  Блоб никуда не отправляется и не попадает в резервные копии (`data_extraction_rules.xml`
  исключает всё). В настройках статистику можно выключить (блоб удаляется, ничего не считается)
  или сбросить с подтверждением. Старые счётчики версий до 0.3.0 один раз переносятся в «за всё
  время» и удаляются.
* **Напоминание о поддержке.** Это карточка на главном экране: уведомлений, будильников, приёмников
  и разрешений нет. Правила (можно ли показывать сейчас, какой текст следующий) — в ядре
  (`arca_attribution::reminder`), одни и те же для всех платформ: показ только 11:00–20:30 по
  местному времени и не чаще раза в 6 дней; текст с числом пропускается, пока число равно нулю.
  Приложение спрашивает ядро при построении главного экрана и держит ответ, пока карточку не
  закроют; в «Настройках» напоминание отключается. Тексты берутся из ресурсов приложения, сеть не
  используется. Нажатие на карточку открывает экран «О приложении», где полный адрес показывается
  раньше, чем открывается по явному нажатию.
* **Дополнительные адреса поддержки** (кошельки, Boosty; задача 51): необязательный список
  `EXTRA_SUPPORT_ADDRESSES` в `crates/arca-attribution/src/support.rs`; пока он пуст, карточка не
  показывается. Основная ссылка поддержки — Lava.top (`https://app.lava.top/pharosteam`). Адрес показывается целиком, копируется только по нажатию
  (`EXTRA_IS_SENSITIVE`, очистка буфера через минуту на Android 9+).
* `allowBackup="false"`, `usesCleartextTraffic="false"`, ни одного провайдера контента,
  экспортирован только `MainActivity` (с фильтрами «Открыть с помощью»).
* **Оформление.** В «Настройках» к режиму «как в системе / светлая / тёмная» добавлена палитра: Classic
  (цвета из ресурсов) и шесть именных — Alabaster Studio (бумажная светлая `#FAF9F6`), Obsidian Vault
  (чёрная `#000000` для OLED; лист страницы в постраничном виде переворачивается по светлоте с сохранением
  оттенка), Cashmere & Cappuccino (кремово-кофейная), Sierra Blue & Slate (холодный титан и сланец), Emerald
  SecOps (тёмно-изумрудная) и Desert Titanium (тёплый графит и бронза). Палитра сама светлая или тёмная,
  системные виджеты следуют за ней. Экраны по-прежнему спрашивают цвет по имени ресурса через `Ui.color`;
  замену делает `ui/Theme`. Переключатель «Жидкое стекло» (по умолчанию выключен) делает карточки и
  баннеры полупрозрачными глянцевыми панелями на мягком цветовом фоне окна; размытия того, что лежит позади
  панели, нет (платформа не даёт его для фона вида на поддерживаемых версиях).
* **Строка таблицы целиком.** Нажатие на номер строки в сетке открывает её как карточку «столбец — значение»:
  для таблиц Access подписи берутся из первой строки (имена столбцов), длинные Memo-поля читаются целиком.
* **Снимки экрана заблокированы по умолчанию** (`FLAG_SECURE`, на Android 13+ ещё и снимок в
  «Недавних»); отключается в «Настройках».
* Автозаполнение и захват содержимого отключены для окна **и для всех диалогов** (диалог — отдельное окно:
  `FLAG_SECURE` и отказ от автозаполнения/захвата применяются к нему отдельно, `Ui.harden`).
* **Буфер обмена.** Скопированное из документа помечается как конфиденциальное
  (`android.content.extra.IS_SENSITIVE`, Android 13+) и очищается через 60 секунд (Android 9+),
  если за это время в буфере не появилось ничего другого; копируется текст, прошедший `Fmt.safe`.
* **Ненадёжный вход.** Ответ ядра длиннее 16 МиБ отвергается до разбора JSON; нехватка памяти и
  любая другая ошибка фоновой задачи приводят к обычному экрану ошибки, а не к зависшему
  состоянию. Кэш картинок ограничен 48 МиБ, страница PDF — масштабом 8 и высотой 32768 пикселей
  (иначе «страница слишком велика»). Невидимые и сбивающие символы Юникода (форматирующие,
  управляющие, частного использования, неназначенные, Hangul-заполнители, U+2800, селекторы
  вариантов, теги) показываются меткой `U+XXXX`; в адресе с не-ASCII хостом дополнительно
  показывается его ASCII-вид (punycode) с предупреждением. Системный классификатор текста для
  ссылок отключён.
* **Источники файлов.** Фильтры «Открыть с помощью» не `BROWSABLE` (веб-страница не может запустить
  приложение) и принимают только `content://`. Адрес `file://` из явного интента принимается лишь
  для обычного файла вне хранилища самого приложения, `/proc`, `/sys` и `/dev` (проверка по
  каноническому пути). Для `content://` файл должен быть обычным: канал (pipe) или сокет, у
  которых нет размера и конца, отклоняются (`ParcelFileDescriptor.getStatSize() < 0`), потому что
  чтение из них могло бы блокироваться без таймаута. **Ограничение:** провайдер, выдающий
  обычный файл с размером, но тормозящий чтение, остановить нельзя — отменить можно только
  разбор.
* Документ не пишется на диск: ни кэша, ни временных файлов. Стерильная копия сохраняется
  только туда, куда укажет человек в системном диалоге.
* После гибели процесса системой (нехватка памяти) открытый документ **не восстанавливается**
  — приложение вернётся на главный экран. Это следствие правила «ничего не сохраняем».
* Ссылки из документа сами не открываются и не загружаются (у приложения нет сети). Нажатие на
  ссылку показывает её **полный адрес** в диалоге с кнопкой «Копировать» — и всё: кнопки
  «Открыть» для ссылок из документа **нет**, ссылку из заражённого файла можно только прочитать
  и, если вы решите, скопировать и открыть самостоятельно. Кнопка «Открыть в браузере»
  (только для `http`/`https`, внешний браузер) есть лишь у собственных ссылок приложения —
  страница проекта, исходный код, поддержка на экране «О приложении».
* Лимиты (размер файла, память песочницы, время) выбираются по устройству
  (`ActivityManager.MemoryInfo`) и не могут быть выставлены ниже безопасных или выше жёстких
  потолков ядра (`EngineConfig::clamped`).

## 5. Сборка

Из исходников, без Gradle: нужен Android SDK (`platforms;android-36`, `build-tools;36.0.0`), NDK
(только компоновщик — C/C++ не компилируется), JDK 17+, Rust 1.97 из `rust-toolchain.toml`.

```sh
bash tools/build-guest.sh                                   # Wasm-гость, хэш печатается
export ARCA_GUEST_WASM=$PWD/target/wasm32-unknown-unknown/guest/arca_guest_xray.wasm
# библиотеки под три ABI (подробно — в .github/workflows/android.yml)
cargo build --release --locked -p arca-jni --target aarch64-linux-android   # и armv7…, x86_64…
# пакет: aapt2 → javac → d8 → zipalign → apksigner → проверка
ANDROID_HOME=… ARCA_NATIVE_DIR=… ARCA_THROWAWAY_KEY=1 bash tools/android/build-apk.sh
```

`tools/android/build-apk.sh` печатает каждый шаг и в конце **проверяет готовый пакет**: имя пакета
и версию, `minSdk 26`/`targetSdk 36`, отсутствие разрешений, три ABI,
несжатые библиотеки с выравниванием 16 КиБ, несжатый `resources.arsc`, наличие сторонних
уведомлений, отсутствие флага отладки, подпись (`apksigner verify`).

Сторонние уведомления (`THIRD_PARTY_NOTICES.txt` в APK, вкладка «Лицензии → Сторонние») строит
`arca-devtools third-party` из графа зависимостей сборки; если у зависимости нет текста лицензии,
он берётся из `tools/third_party_licenses/`, а при его отсутствии сборка останавливается.

Локально собирать можно в WSL/Linux (шаги — в [README](../README.md#сборка) и [RELEASING](RELEASING.md)); локальный пакет
подписывается одноразовым ключом (`ARCA_THROWAWAY_KEY=1`), релизный ключ на машине разработчика для этого не нужен.

Подпись: релизным ключом — **только для тегов `v*`**: секреты ключа лежат в окружении `release`
репозитория и доступны единственному заданию `package-release`, которое передаёт их шагам через
`env:` (не через `GITHUB_ENV`); сборки pull request и ветки `main` секретов не видят и подписываются
**одноразовым ключом**, созданным на время сборки (пакет честно помечается; обновить его пакетом с
другим ключом нельзя — только удалить и поставить заново). Если в окружении `release` ключа нет,
релиз тоже получает одноразовый ключ и пометку об этом. Тег разбирается строго (`vМАЖОР.МИНОР.ПАТЧ`,
каждая часть — число), `versionCode` = МАЖОР·1 000 000 + МИНОР·1 000 + ПАТЧ.

## 6. Что проверено, а что нет

Автоматически (CI, при каждом изменении):

| Проверка | Что доказывает |
|---|---|
| `cargo clippy --workspace --all-targets -D warnings`, `cargo fmt --check` | код ядра чист на уровне политики проекта: без `unwrap`/`expect`/`panic`/индексации вне тестов |
| `cargo test --workspace`, в `release` со сквозным прогоном гостя | форматы, лимиты, мутационный фаззинг, песочница, таблицы враждебных входов с точными вердиктами (число тестов смотрите в журнале CI: после раунда проверки 0.2.2 оно выросло, прежняя цифра в этом файле устарела) |
| `e2e_sandbox` с реальным гостем и корпусом документов | результат гостя в песочнице совпадает с нативным разбором, отмена и дедлайн работают, бомбы останавливаются |
| `tools/check-unsafe.sh` | `unsafe` только в `ffi.rs` и таблице экспортов гостя; нет `*-sys`/`cc` в графе |
| `tools/android/check-android.sh` | ресурсы и манифест согласованы на обоих языках, приложение компилируется против API 26 и 36, новее 26 — только в `Compat`, чистая Java-логика (`android/core-test`) |
| `android/host-test/run.sh` | все `native`-методы на JVM с `-Xcheck:jni`; настоящие документы из `tests/fixtures` и сгенерированные входы, мутации (`ARCA_FUZZ_ITERS` — больше), постраничная выдача, скрытое содержимое, согласие таблицы возможностей приложения с движком, документ без единого раздела (число проверок смотрите в журнале CI) |
| `arca-devtools elf-check`, `zipalign -c -P 16`, `apksigner verify`, `aapt2 dump badging` | пакет подписан, библиотеки выровнены, нет разрешений |
| Эмуляторы API 26, 28, 30, 31, 33, 34, 35, 36 (x86_64) | *проверяет*, что пакет ставится, запускается, переживает 14 форм окна и поворот, крупный шрифт, тёмную тему, открытие 16 документов, без падений/ANR. Результаты и снимки экранов сохраняются в артефактах запуска |

**Ручное тестирование на устройствах:**

* внешний вид, удобство и стабильность интерфейса на физических Android-устройствах (различные
  форм-факторы экрана, адаптивная компоновка, светлая/тёмная темы, системные панели, жесты навигации);
* работа локальных офлайн-напоминаний о поддержке разработчиков (Pharos Team / Lava.top);
* отсутствие сетевых соединений во время работы.

**Распространение и обновления.** Сейчас приложение распространяется подписанным APK в
[GitHub Releases](https://github.com/Johnny-Wickky/arca/releases). В приложении нет самозагрузчика
и нет сети (разрешения `INTERNET` нет), поэтому оно обновляется установкой новой версии поверх старой:
пользователь скачивает новый APK, сверяет SHA-256 и ставит поверх старого. Android принимает обновление,
только если оно подписано тем же ключом.

## 7. Известные ограничения

* Сгиб гибкого экрана угадывается по форме экрана и углу шарнира, шарнир двухэкранного устройства берётся из выреза; на физическом складном устройстве ни то, ни другое не проверялось (§3).
* Поиск по документу, оглавление, закладки и масштаб есть (§1); масштаб запоминается и не
  применяется к постраничному виду.
* Просмотр показывает **содержание**, а не точную вёрстку: документы — абзацы, таблицы, сноски,
  комментарии и заметки; у PDF есть приблизительный постраничный вид (градиенты и узоры плоским
  цветом, шрифты заменены). Картинки в тексте — заглушки с размером; по тапу их раскодирует
  песочница (§1).
* Зашифрованные документы открываются с паролем (Office 2007/2010+, PDF); OpenDocument и старые бинарные форматы — нет, для них остаётся вердикт «Не проверено». Пароль вводится в диалоге; массивы `char[]`/`byte[]` на стороне Java затираются сразу после передачи, но пока документ открыт, пароль остаётся в памяти процесса (его держит ядро, чтобы разбирать документ), и стирается при закрытии документа. На диск он не попадает; копии в памяти клавиатуры и виртуальной машины приложение стереть не может.
* Стерильная копия строится для OOXML, Visio OOXML, OpenDocument, PDF, DOC/XLS/PPT/RTF и картинок (§1); для остальных форматов её нет.
* Аудитория программ чтения с экрана: есть подписи и заголовки, но полноценного прохода
  TalkBack по всем экранам на устройстве не делалось.
