# Arca — архитектура

> Статус: **Фазы 1–4 реализованы для Android** (архитектура, лицензирование, песочница, рентген
> угроз, стерилизаторы, безопасный просмотр, `arca-engine`/`arca-jni`, приложение). Фаза 5
> (фаззинг и враждебные входы) выполнена частично. Клиент iOS (`arca-ffi`, `app/`) написан, но не
> собирался и не проверялся при последней проверке (0.2.2): он описан в §4.10 как «есть в
> репозитории», а не как «работает». Места, помеченные *(Фаза N)*, — по-прежнему план.

## 1. Принципы

1. **Каждый файл — враждебный эксплойт.** Ни один байт документа не
   интерпретируется вне двух контуров изоляции: memory-safe Rust и
   эфемерной Wasm-песочницы без импортов.
2. **Ноль `unsafe`, ноль C/C++.** Весь собственный код —
   `#![forbid(unsafe_code)]`; в графе зависимостей нет `*-sys`-крейтов и C-сборки.
   Единственное ограниченное исключение — атрибут `#[unsafe(no_mangle)]` на
   пяти экспортах Wasm-гостя (§4.6).
3. **Детерминированные отказы.** Ни `unwrap`/`expect`/`panic` в рабочем коде,
   лимит на всё, что зависит от входа: размер, глубина, число элементов,
   коэффициент сжатия, топливо CPU, память.
4. **Никакой сети.** Ядро не содержит сетевого кода; приложению не нужно
   разрешение `INTERNET`. Внешние ссылки документа только перечисляются в
   отчёте. Ссылки на пожертвования открывает системный браузер, и только
   после явного нажатия пользователя.
5. **Без утечек.** Буферы документов, пароли, результаты и ключи шифрования, которыми владеет Arca,
   обнуляются (`zeroize`: `Zeroizing`, обнуление при `Drop`); `Debug` у хоста, документа, результата
   и ответа гостя печатает размеры, а не содержимое. Копии, оставленные аллокатором или зависимостями,
   стереть нельзя (§8). Логи не содержат содержимого документов и персональных метаданных: ядро
   вообще ничего не логирует.

Граф зависимостей реализованных крейтов (стрелка — «зависит от»):

```text
arca-attribution ─► arca-digest ◄─ arca-sandbox ─► arca-abi
                                           ▲    └─► wasmi, wasmi_core, zeroize
arca-guest-xray ─► arca-xray ─► arca-container ─► arca-digest
        │      └──► arca-preview ─► arca-container, arca-abi, arca-xray, arca-image
        └─► arca-abi ◄──┘                        └─► quick-xml, miniz_oxide (arca-container: + zeroize)

          ├─► arca-engine ─► arca-sandbox, arca-abi, arca-attribution, arca-guest-xray, arca-container,
arca-ffi ─┘                  arca-image, arca-digest, zeroize
```

`arca-sandbox` не зависит от `arca-xray`: сам хост песочницы не содержит парсеров документов.
Отчёт из песочницы декодирует тонкий слой `arca_guest_xray::decode_report` с жёсткими
лимитами декодирования. `arca-engine`, который стоит над песочницей, зависит от `arca-container`
и `arca-image` и **использует их вне песочницы** в трёх местах (§4.9): чтение центрального
каталога ZIP для подсказки бюджета, проверка имён частей стерильной копии и определение картинки
по первым байтам. «Хост без парсеров» поэтому верно только для `arca-sandbox`.

## 3. Два контура изоляции

```text
 ┌──────────────────────────── процесс приложения ─────────────────────────────┐
 │  Android-приложение (Java) ──JNI──► arca-jni ─► arca-engine                │
 │                                   │ дескриптор файла → память ядра          │
 │                                   ▼                                         │
 │  ┌──────────── arca-sandbox (хост, Safe Rust) ───────────────────────────┐ │
 │  │ 1. проверка SHA-256 модуля по allow-list (ModulePin)                    │ │
 │  │ 2. валидация модуля, отказ при ЛЮБОМ импорте, start-функции, лишних     │ │
 │  │    proposals                                                            │ │
 │  │ 3. новый Engine + Store на один вызов, отдельный рабочий поток          │ │
 │  │ 4. лимиты: память (по размеру входа), топливо CPU порциями, дедлайн,    │ │
 │  │    отмена, глубина рекурсии, стек                                       │ │
 │  │  ┌────────── Wasm-гость (wasm32-unknown-unknown, 0 импортов) ──────────┐ │ │
 │  │  │ arca-guest-xray = arca-xray + arca-preview + arca-container      │ │ │
 │  │  │ нет сети, ФС, таймера, случайности, IPC — только вычисления         │ │ │
 │  │  └─────────────────────────────────────────────────────────────────────┘ │ │
 │  │ 5. копия результата с проверкой границ → конверт ARCA → wire-декодер    │ │
 │  │ 6. обнуление памяти гостя, уничтожение Store                            │ │
 │  └────────────────────────────────────────────────────────────────────────┘ │
 └──────────────────────────────────────────────────────────────────────────────┘
```

**Контур 1 — Safe Rust.** Исключает целые классы уязвимостей парсеров
(переполнение буфера, use-after-free, double free). Остаются логические
ошибки и отказ в обслуживании; их закрывают лимиты и контур 2.

**Контур 2 — эфемерная песочница.** Даже если в парсере есть логическая
ошибка, позволяющая документу управлять его поведением, у гостя нет никакой
возможности воздействовать на мир: модуль без импортов может только считать в
своей линейной памяти. Время и память ограничены, после вызова от экземпляра
не остаётся ничего.

## 4. Крейты

### 4.1 `arca-digest`
SHA-256 (FIPS 180-4, проверка по векторам NIST) и CRC-32 (IEEE 802.3), `no_std`,
без зависимостей. SHA-256 пиннингует Wasm-модули и отпечаток уведомления об
авторстве. CRC-32 используется только для целостности ZIP и записи
статистики «Паспорта».

### 4.2 `arca-container` — защищённые контейнеры
| модуль | что делает | ключевые защиты |
|---|---|---|
| `zip` | чтение ZIP/ZIP64 по центральному каталогу | EOCD/ZIP64-валидация; **двусмысленный EOCD** (другая запись EOCD/ZIP64 после начала выбранного каталога, например настоящий каталог спрятан в комментарии записи) — отказ; согласие CD ↔ локальных заголовков (имя, метод, размеры, CRC, маркеры ZIP64 в локальном extra); **дескрипторы данных** читаются и сверяются с каталогом; поток deflate должен занять ровно заявленный сжатый размер; запрет перекрытий записей; **зазоры** между записями — аномалия `UnreferencedData`, лишние байты за каталогом — `TrailingData`, комментарии — аномалии; **Unicode Path (0x7075)**, называющий часть иначе, — отказ; канонизация имён (см. ниже), дубликаты без учёта регистра, symlink-атрибуты; коэффициент ≤ 100:1 (запас 1 МиБ); обнаружение «лживого» размера; общий бюджет распаковки на документ (`InflateBudget`, 1 ГиБ; агрегатный коэффициент считается от **длины исходного файла**, а не от вложенного потока) |
| `zip::name` | проверка имени части | отказ при `../`, абсолютных путях, `\`, буквах дисков, NUL и управляющих символах, bidi-управляющих и **невидимых** (категории Cf/Zl/Zp, теги, заполнители, селекторы вариантов), `:`, **точке или пробеле в конце компонента**, закодированных `%2e`, `%2f`, `%5c` |
| `zip::writer` | детерминированная запись (стерилизатор) | фиксированная метка времени, проверка имён |
| `cfb` | OLE2 Compound File | проверка заголовка и сектора; DIFAT/FAT/miniFAT с обнаружением циклов; **у каждого сектора один владелец** (FAT, DIFAT, каталог, mini-FAT, поток): сектор, общий для двух потоков, — `CrossLinked`, отказ; **бюджет чтения** потоков за жизнь файла (`max_total_read`, 1 ГиБ); ограничение числа записей каталога, размера потоков, глубины и памяти под пути; обнаружение «осиротевших» записей |
| `cfb::writer` | детерминированная запись CFB | — |
| `xml` | безопасный потоковый XML поверх `quick-xml` | `DOCTYPE` запрещён целиком (XXE, Billion Laughs); только пять предопределённых сущностей и числовые ссылки; глубина ≤ 64; лимиты атрибутов, событий, длины имён и входа; ровно один корень; перекодировка UTF-16 **только с BOM**: UTF-16/32 без BOM и EBCDIC отвергаются по первым байтам, `encoding=` в декларации обязано совпасть с байтами; допускаются только символы `Char` XML (NUL, управляющие C0, U+FFFE/FFFF — ошибка кодировки); при переписывании UTF-16 → UTF-8 декларация исправляется |
| `xml::rewrite` | перезапись с сохранением исходных байтов вне изменённых узлов | основа стерилизатора |
| `jet` | чтение баз Access (Jet 3 / Jet 4 / ACE): страницы, каталог `MSysObjects`, строки таблицы | общее для рентгена и просмотра; цепочки страниц, переполнений и длинных значений с проверкой циклов (множество посещённых), ограничения на число страниц определения, колонок, строк (4 000 000), длинное значение ≤ 4 МиБ, **счётчик работы на один обход** (1 000 000 единиц: колонки, читающие одни и те же байты, не умножают работу); шифрованная база — `Encrypted` |
| `crypto` | MD5, SHA-1/2, AES, RC4 — для расшифровки Office и PDF | таблицы ключей AES и состояние RC4 не клонируются, их `Debug` ничего не показывает, при `Drop` обнуляются (`zeroize` — зависимость `arca-container`); CBC требует целых блоков; снятие PKCS#7 не различает причин отказа |
| `text`, `bytes`, `budget` | безопасное чтение little-endian, кодовые страницы, обезвреживание bidi- и невидимых символов при показе | — |

### 4.3 `arca-abi` — контракт гостя (версия 5)

| экспорт | сигнатура | смысл |
|---|---|---|
| `memory` | память | единственная память гостя |
| `arca_abi_version` | `() -> i32` | должна вернуть `5` (`ABI_VERSION`) |
| `arca_input_reserve` | `(len) -> ptr` | гость выделяет буфер под вход |
| `arca_run` | `(len) -> status` | обработка |
| `arca_output_ptr` / `arca_output_len` | `() -> i32` | где лежит результат |

История версий: v2 — заголовок запроса с операцией (рентген, стерилизация, просмотр); v3 — пароль в
префиксе запроса; v4 — операция `Render` (страница PDF); v5 — операция `Image` и флаг `FULL_SIZE`
у `Sanitize`. Гость другой версии песочницей не запускается. (Комментарий в шапке `crates/arca-abi/src/lib.rs`
всё ещё говорит «version 3»; константа `ABI_VERSION` равна 5.)

Запрос: `"ARCQ" | u16 версия | u16 операция | u32 флаги | u32 длина пароля | пароль | документ`.
Результат — конверт `"ARCA" | u16 версия | u16 вид | u32 длина | полезная нагрузка`.
Нагрузка кодируется собственным wire-кодеком с ограниченным декодированием: данные из песочницы
считаются недоверенными, ведь скомпрометированный гость мог записать что угодно. `DecodeLimits` —
длина строки, число элементов в последовательности, глубина; сверх этого у декодера есть **общий
бюджет памяти** (`DEFAULT_TOTAL_BYTES`, 256 МиБ): каждая последовательность оплачивает
`число × размер элемента в памяти`, каждая строка — свою длину, выделение идёт через
`try_reserve` порциями. Без бюджета один байт на проводе (например, `Block::Rule`) превращался бы
в десятки байт в памяти; бюджет закрывает такое усиление. Лимиты для каждого вида результата задаёт
`limits_for` в `arca-guest-xray`.

### 4.4 `arca-xray` — «Рентген безопасности»

`scan(bytes, &ScanPolicy) -> XRayReport` — один проход без исполнения чего-либо.

**Определение формата** — только по сигнатурам (ZIP `PK`, OLE2
`D0 CF 11 E0 A1 B1 1A E1`, `%PDF`, `{\rtf`, Jet/ACE, MZ/ELF/Mach-O), уточнение
по `[Content_Types].xml`, `mimetype` ODF и CLSID корня OLE2. Расширение файла не
используется. Поддерживаемые семейства: OOXML (docx/docm/dotx/dotm, xlsx/xlsm/
xltx/xltm/xlsb/xlam, pptx/pptm/ppsx/ppsm/potx/potm, vsdx/vsdm/шаблоны, xps), ODF
(odt/ods/odp/odg), OLE2 (doc/xls/ppt/vsd/msg/msi, зашифрованный OOXML), RTF,
PDF, Access (Jet3/Jet4/ACE), текстовые (txt/csv/tsv/md/html/flat XML), ZIP,
исполняемые файлы (отказ).

**Детекторы** (каждая находка — типизированный `ThreatKind` с категорией и
важностью):

* *Активное содержимое:* VBA (MS-OVBA: распаковка, разбор `dir`, извлечение
  исходников, автозапуск, подозрительные вызовы, признаки VBA stomping), XLM
  Excel 4.0 (макролисты, `Auto_Open`), StarBasic/скрипты ODF, DDE в полях Word
  (включая обфускацию `QUOTE`) и в формулах, `WEBSERVICE`/`CALL`/`REGISTER`,
  OLE-объекты и пакеты (`Ole10Native`, опасные расширения, таблица опасных
  CLSID — Equation Editor и др.), ActiveX, callbacks ленты, действия PowerPoint
  `ppaction://program`, `RUNADDON` в Visio, RTF `objdata`/`objupdate`, PDF
  JavaScript/Launch/OpenAction/вложения/RichMedia, CSV-инъекции формул, активный
  HTML.
* *Внешнее содержимое (SSRF, трекеры, NTLM-утечки):* удалённые шаблоны
  (`attachedTemplate`), внешние картинки и фреймы, связанные OLE-объекты,
  внешние книги, подключения данных, `INCLUDEPICTURE`/`INCLUDETEXT`, UNC-пути,
  опасные схемы URI (`ms-msdt:` и т. п.), источники слияния, удалённые действия
  PDF, `hyperlinkBase`. Каждый URL попадает в `external_refs` с
  классификацией цели.
* *Сокрытие:* скрытые и «очень скрытые» листы, скрытые строки и столбцы,
  скрытый и невидимый (белым по белому, микрошрифт) текст, скрытые слайды,
  осиротевшие OLE-записи и данные ZIP, полиглоты (PDF+ZIP и др.), хвостовые
  данные, bidi-переопределения в именах, переменные документа.
* *Утечки приватности:* автор, организация, компьютер, локальные пути,
  принтеры, ревизии, комментарии, идентификаторы сеансов правки (rsid),
  пользовательские свойства, суммарное время правки, версии ПО.
* *Структура:* повреждённые контейнеры, бомбы, обход путей, XML-атаки,
  расхождения парсеров, несоответствие типа содержимого, замаскированные
  исполняемые файлы, шифрование.

**Вердикт** (`Verdict`) — результат слияния, в котором побеждает наиболее
серьёзное состояние:
`Rejected` (бомба, обход путей, XML-атака, исполняемый файл и т. п. — документ не
открывается) > `ActiveContentNeutralized` (активная нагрузка или критическое
внешнее содержимое, например удалённый шаблон) > `Unverified` (часть документа
**не удалось проверить**) > `HiddenTrackers` (есть внешнее содержимое) > `Clean`.

Два свойства важны для доверия к значку «Чистый»:

* вердикт вычисляется из *фактов* (`Facts`), которые копятся независимо от
  ограничения на число сохраняемых находок. Документ, в котором 5 000 безобидных
  находок вытеснили единственный макрос из отчёта, всё равно получает
  `ActiveContentNeutralized` (регрессия A-1, тесты `a1_*` в `crates/arca-xray/src/tests/verdict.rs`);
* `Clean` означает «проверено целиком, и каждое прочтение однозначно». Зашифрованная часть,
  не разобранный XML, часть сверх лимита или пропущенный вложенный документ дают `Unverified`,
  а не `Clean` (регрессия A-3, тесты `a3_*`). Стерилизатор тоже не выдаёт копию, содержащую
  непроверенные части.

**Пробелы покрытия.** Находка делает `Clean` невозможным («пробел покрытия»,
`ThreatKind::limits_coverage` / `limits_coverage_at(severity)`), какой бы у неё ни была важность:
`MalformedContainer`, `UnusualCompression`, `ScanLimitReached`, `EncryptedDocument`,
`EncryptedMember`; **добавлены**: `ParserDifferential` (второй читатель увидел бы другой документ),
`PolyglotFile`, `UnreferencedArchiveData` (байты архива, на которые ничто не ссылается),
`OrphanedOleEntries`, `ObfuscatedName`; **зависящие от важности**: `TrailingData` — с `Low`
(на `Info` — только проверенное нулевое заполнение) и `ContentTypeMismatch` — с `Medium`. Что из
этого следует для разных форматов:

* **OOXML:** роль части (`ooxml/role.rs`, одна на сканер и стерилизатор) определяется по типу
  содержимого, затем по типу связи, и лишь в последнюю очередь по имени; несогласие источников —
  находка, часть сканируется под самой авторитетной ролью. Имя `word/mycomments.xml` у основной
  части больше не пропускает её текст. Архив, который одновременно OPC и ODF, сканируется как оба.
  Атрибуты с одним локальным именем под разными префиксами (`w:instr` и `foo:instr`, `a:Target` и
  `Target`) — расхождение читателей (`ParserDifferential`); ODF, где это штатно, проверку отключает.
* **Поля Word:** вложенные поля (`{ {QUOTE "DDEAUTO"} … }`, REF, SET, DOCVARIABLE) разворачиваются:
  ключевое слово, поставленное вложенным полем, — находка (в OOXML, бинарном Word и RTF; в RTF
  вложенные `\fldinst` ведутся стеком по глубине групп, `\ucN` учитывается).
* **PDF:** настоящий разбор словаря потока (вложенные `/DecodeParms`), фильтры `ASCIIHex`,
  `ASCII85`, `RunLength`, `LZW`, `Flate` с предикторами — в цепочках и с ограничением вывода;
  неподдержанный фильтр или параметр — «поток не прочитан» (`ScanLimitReached`), а не пропуск.
* **Текст:** кроме CSV/TSV/SYLK/Markdown/HTML, плоский XML разбирается по корневому элементу
  (плоский OPC, Word 2003 XML, Excel 2003 XML, плоский ODF, SVG); неизвестный корень —
  `ScanLimitReached` (то есть `Unverified`). Файлы, которые Windows или интерпретатор запускают
  по содержимому (`.url`, `.scf`, `.theme`, `.iqy`, `.library-ms`, `.settingcontent-ms`, `.sct`,
  `.wsf`, `.jnlp`), на верхнем уровне — `DisguisedExecutable` (`Rejected`), внутри другого файла —
  `EmbeddedExecutable`; текст со скриптом (VBS/JS/пакетный/PowerShell) — `EmbeddedScript` (High).
  Разметку (`<script>`, `onload=`, `meta refresh`) ищут в любом тексте.
* **Access:** *закрыт по умолчанию к отказу*. Побайтовый поиск имён `AutoExec`, `VBAProject`,
  `MSysAccessStorage` (ASCII и UTF-16LE, без учёта регистра) идёт независимо от разбора; затем
  читается каталог. Каталог не открылся, оборван, шифрован или версия неизвестна —
  `MalformedContainer` / `ScanLimitReached` / `EncryptedDocument`, то есть `Unverified`. Связанные
  таблицы попадают в `external_refs`. Следствие побайтового поиска: безобидная база, где эти слова
  встречаются как данные, получит находку (ложное срабатывание принято сознательно, см. модель
  угроз §4.17).
* **Цели ссылок:** классификация после процентного декодирования (до трёх раундов) и с любой
  смесью `/` и `\` в начале (`\/host`, `/\host`, `file:///%5C%5Chost`); `smb:`, `ms-outlook:`,
  `outlook:`, `onenote:`, `ms-onenote:` и любая схема `ms-*` — опасные протоколы.

Классификация целей: `file:`-URL с UNC-хостом, схемно-относительные `//host/…` и
обратные косые черты `\\host\…` считаются сетевыми (утечка NTLM-хеша), а не
локальными файлами (A-2, F-4). URL внутри формул Excel (`HYPERLINK`, `WEBSERVICE`,
`IMAGE`, DDE-строки, ссылки на внешние книги) попадают в `external_refs` так же,
как URL в связях пакета (F-3). Быстрый предфильтр (`formulas::may_contain_risk`)
отсеивает формулы без рискованных слов; тест `prefilter_is_a_superset` следит,
чтобы он не пропускал ничего, что находит полный разбор.

**Стерилизатор** (`sanitize`) — *One-Tap Sanitize* для OOXML: удаляет части по
ролям (VBA, ActiveX, OLE, макролисты, customXml, миниатюры, комментарии),
внешние и висячие связи; переписывает XML: нейтрализует поля (DDE,
`INCLUDE*`, `MACROBUTTON`), принимает ревизии, удаляет комментарии, rsid и
метаданные, удаляет опасные формулы Excel с сохранением закэшированных значений,
действия PowerPoint, активные формулы Visio; меняет типы содержимого на
безмакросные (`docm` → `docx`). Результат детерминирован, идемпотентен и
**сканируется повторно**: копия выдаётся, только если в ней не осталось
активного или внешнего содержимого уровня Medium и выше и вердикт повторного
сканирования не `Rejected` и не `Unverified`. Определение роли части общее со сканером
(`ooxml/role.rs`), поэтому сканер и стерилизатор больше не «решают одно и то же двумя
способами»; UTF-16-части при перезаписи переводятся в UTF-8 вместе с декларацией
(`xml::declare_utf8`). Повторная проверка всё равно делается теми
же сканерами, что и первая, — она ловит то, что стерилизатор забыл убрать, но не то, чего не видит сам
сканер; хост добавляет сверху свою «растяжку» (§4.9).

Для остальных форматов копия строится иначе (подробно — модель угроз §4.12–4.14, §4.20): ODF
пересобирается без активных и внешних частей; PDF строится заново из того, что нужно страницам;
DOC/XLS/PPT/RTF пересобираются в новый OOXML по результату просмотра (`arca-preview::export`);
картинка — новый PNG из пикселей. Ссылки в пересобранной копии становятся видимым текстом с
адресом в скобках.

### 4.5 `arca-sandbox` — хост песочницы

| свойство | механизм |
|---|---|
| нет системного доступа | модули с **любым** импортом отвергаются до инстанцирования |
| нет внедрения кода | исполняются только модули с SHA-256 из allow-list; валидация всегда включена; `start` запрещён; лишние proposals выключены |
| CPU | топливо: `2·10⁹ + 32 000 × байт входа`, максимум по умолчанию `4·10¹¹` (`FuelPolicy::DEFAULT.max`; в 0.2.0 было ошибочно поднято до `2·10¹²`, возвращено); исчерпание — детерминированная ловушка. Больше этого может выдать только вызывающий (`arca-engine`, §4.9), и не выше своей фиксированной константы |
| **время** | топливо выдаётся гостю **порциями** (`slice_fuel`, 25·10⁶ ≈ 10 мс); между порциями хост проверяет монотонный дедлайн (`max_wall_time`, по умолчанию 300 с, или `RunOptions::deadline`; предел больше 7 суток, например `Duration::MAX`, обрезается до 7 суток, а не превращается в «без предела»). Медленное устройство не превращает большой бюджет топлива в бесконечное ожидание. Нарезка не меняет *сколько* гость может вычислить — только как часто хост смотрит (инвариант проверен тестами: расход топлива идентичен при любой порции) |
| **отмена** | `CancelToken` опрашивается на каждой границе порции: UI прерывает разбор за миллисекунды, не убивая процесс. Гость не видит ни токена, ни времени (нет импортов, нет таймера — защита от timing side-channel) |
| **прогресс** | необязательный `on_progress` получает `Progress { fuel_consumed, fuel_limit, elapsed }`; паника в обработчике перехватывается и не ломает песочницу |
| память | `ResourceLimiter`: `min(1 ГиБ, 96 МиБ + 4 × байт входа)` линейной памяти (для обычного небольшого файла около 96 МиБ — в духе «128 МиБ» спецификации), 100 000 элементов таблиц |
| стек | лимит глубины рекурсии интерпретатора (4096) и высоты стека значений (8 МиБ); нативный стек рабочего потока 8 МиБ |
| ввод-вывод | вход ≤ 512 МиБ, выход по умолчанию ≤ 64 МиБ (`max_output_bytes`; `arca-engine` задаёт по операции — §4.9), модуль ≤ 32 МиБ; регион результата проверяется на границы памяти гостя; буфер под результат выделяется через `try_reserve_exact` (нехватка памяти — ошибка запуска, не падение приложения) и не копируется второй раз |
| эфемерность | `Engine`/`Store`/память — на один вызов; линейная память гостя обнуляется стражем `MemoryZeroizeGuard` при `Drop` (в том числе при раскрутке стека после паники хоста; при аварийном завершении процесса, `abort` или убийстве процесса обнуления не будет — это не «гарантированное» стирание, а добросовестное); результат в `Zeroizing`; `Debug` результата запуска показывает размер, не содержимое |
| локализация сбоев | гость выполняется в отдельном потоке (`std::thread::scope`); паника интерпретатора → `SandboxError::WorkerPanicked` |

**Калибровка бюджета** (регрессия B-1: обычная таблица в 100 КБ раньше упиралась в
лимит 4000 топлива/байт и отвергалась как «слишком сложная»). Измерено на
настоящем госте (`cargo run --release -p arca-guest-xray --example measure`):

| документ | байт | топливо на байт входа |
|---|---|---|
| Word, текст (сжатие ≈ 10:1) | 750 КБ | ≈ 4 400 |
| Excel, случайные числа (≈ 5:1) | 0,1 – 8 МБ | ≈ 5 800 – 6 100 |
| Excel, однотипные ячейки (≈ 10:1) | 650 КБ | ≈ 14 400 |

Таблицы — худший случай: миллионы крошечных элементов, около 1 300–1 450 единиц
топлива на байт XML. Бюджет 32 000/байт допускает таблицы со сжатием до ≈ 20:1 и
всё ещё останавливает убежавший цикл за секунды. Скорость интерпретатора
зависит от устройства (на разработческой машине 2–4,6·10⁹ топлива/с; книга в
8 МБ — около 10 с), поэтому *время* ограничивают дедлайн и отмена, а не топливо.

**Диспетчеризация `wasmi`.** Сборка `release` использует диспетчеризацию через
хвостовые вызовы (`auto-dispatch`); она примерно на 40 % быстрее переносимой
(675 мс против 1100 мс на таблице в 500 КБ при одинаковом расходе топлива), поэтому
`portable-dispatch` не выбран. В профиле `dev` с повышенной оптимизацией `wasmi`
нативный стек рабочего потока переполнялся (даже 16 МиБ), поэтому такое
переопределение запрещено комментарием в корневом `Cargo.toml`, а сквозные тесты
гостя в CI идут в `--release`.

`wasmi` (интерпретатор) выбран вместо JIT-рантаймов, потому что iOS не даёт
сторонним приложениям исполняемую память (W^X), а интерпретатор не пускает
код гостя в машинный поток инструкций вовсе.

### 4.6 `arca-guest-xray` — гость
`arca-xray`, собранный под `wasm32-unknown-unknown` профилем `guest`
(`panic = "abort"`, `opt-level = 3`, полный LTO). Для интерпретируемого гостя скорость важнее размера:
сборка `s` была на ≈ 35 % медленнее на настоящих таблицах при модуле меньше на ≈ 12 %. Модуль имеет **ноль импортов**
(проверяется в CI и при каждом запуске). Экспорт символа требует атрибута
`#[unsafe(no_mangle)]`, который линт `unsafe_code` считает небезопасным, поэтому
крейт использует `deny` вместо `forbid` и разрешает его ровно на пяти
функциях экспорта. Блоков `unsafe` нет; `tools/check-unsafe.sh` проверяет и это,
и идентичность остальных линтов. Отчёт гостя совпадает с нативным сканированием
(тест `guest_report_equals_native_report` и прогон по корпусу).

### 4.7 `arca-attribution` — атрибуция и «Паспорт Хранителя»
* `upstream.rs` — неизменяемые константы оригинальных создателей
  (`UPSTREAM_AUTHORS`, `UPSTREAM_DONATION_LINKS`, тексты уведомления, заголовки
  карточек). Их SHA-256-отпечаток закреплён в `UPSTREAM_FINGERPRINT`;
  `build.rs` останавливает сборку при любом расхождении. Это защита от
  случайного удаления, а не DRM: юридическую силу имеет лицензионное условие.
* `fork.rs` — строгий разбор `fork_attribution.toml` (подмножество TOML, только
  известные ключи, только `https://`, без учётных данных, управляющих и
  bidi-символов, запрет выдавать себя за оригинал). Тот же код выполняется в
  `build.rs`: некорректный файл форка не компилируется.
* `screen.rs` — модель экрана «О проекте и Поддержка»: карточка «Создатели
  оригинального ядра Arca (Поддержать)» всегда первая, карточка
  «Команда поддержки модификации / Форка (Поддержать)» добавляется в форке,
  у карточек нет индивидуального стиля. `check_upstream_prominence` проверяет
  отрисованную раскладку в golden-тестах UI.
* `passport.rs` — локальная статистика (36-байтовая запись с CRC, без часов и
  ввода-вывода в ядре) и текст «Вы пользуетесь Arca уже 30 дней…» с
  правилами русских склонений.
* `integrity.rs` — отпечаток и блокировщики релиза: `ARCA_RELEASE=1` не
  собирается, пока остались домены-заглушки (`.invalid`, `.example`, …).

Идея обязательной атрибуции в интерфейсе заимствована из CPAL-1.0 (Exhibit B),
но требование мягче: экран «О проекте и Поддержка», а не заставка при каждом
запуске. Юридическая основа — дополнительные условия по разделу 7 AGPLv3, а
не CPAL: CPAL несовместима с GPL.

### 4.8 `arca-image` — картинки

Декодеры PNG, JPEG (baseline и progressive, с уменьшением прямо при разборе блоков), GIF и BMP, чтение
EXIF (положение, серийный номер, миниатюра, поворот) и запись PNG для стерильной копии. Как и
`arca-container`, крейт не выполняет ввод-вывод, не создаёт потоков, не читает часов и собирается в
гость. Наружу выходит только ограниченный растр RGBA и «факты» о том, что было отброшено (см.
[IMAGES.md](IMAGES.md)). Идентификаторы картинок внутри документов задаёт `arca-preview`
(`picture.rs`: OOXML/ODF — номер файла контейнера, PDF — номер объекта, RTF — смещение `\pict`).

**Учёт байт.** Каждый декодер ведёт учёт: что картинка, что структура формата, что распознанные
метаданные. Всё остальное (приватные блоки PNG и маркеры JPEG, тело `IEND`, хвост zlib/LZW после конца
потока, неизвестные расширения GIF, зазор между палитрой и `bfOffBits` в BMP, лишние байты в заголовках
JFIF/Adobe) складывается в `Facts::unaccounted` и выходит в «Рентген»; `arca-xray` всегда проверяет картинку на
полиглот по всем байтам. EXIF читается без потолка в 512 записей (раньше указатель на GPS мог оказаться
после него), с указателями типов 9 и 13; флаг свободного текста ловит `ImageDescription`, `UserComment`
и поля `XP*`. Границы: сторона и площадь проверяются до выделения памяти (кадр GIF — сам по себе),
потоковое декодирование — до 64 Мпкс, режимы, которым нужен весь растр (прогрессивный JPEG,
чересстрочные PNG/GIF, RLE в BMP), — до **16 Мпкс** (`max_buffered_pixels`), проходов JPEG не больше 200, RLE в
BMP ограничен шириной и общим объёмом работы. Стерильный PNG после записи читается обратно строго
(`decode_sterile`: CRC всех чанков, Adler-32, ни хвоста, ни метаданных, ни необъяснённых байт, один кадр).
Чего учёт не видит: содержимое энтропийных данных JPEG и сами пиксели (стеганография).

### 4.9 `arca-engine` — хост-слой для приложений

Один `Host` на процесс; наружу выходят только счётчики-дескрипторы (документы, задания, результаты),
никогда указатели. Документ собирается в `Zeroizing`-буфере, растёт «с зачисткой» (новый блок строится
рядом, старый стирается), пароль хранится отдельно и стирается вместе с документом.

| что | как |
|---|---|
| лимиты устройства | `EngineConfig`: вход 256 МиБ, память гостя 768 МиБ, рентген 120 с, просмотр 180 с; `clamped()` не даёт выйти за 1–512 МиБ, 160 МиБ–1 ГиБ, 5–600 с и 5–900 с |
| топливо и память по операции | базовый бюджет песочницы (`2·10⁹ + 32 000/байт`, по умолчанию не выше `4·10¹¹`) плюс подсказка о том, во что документ распаковывается: просмотр получает 1 500, стерильная копия 6 000 единиц топлива на распакованный байт (и 2/4 байта памяти), рентген — 1 500 за байт сверх 20:1. Подсказка — цифра предыдущего рентгена (`bytes_inflated`), а при её отсутствии — `sniff_inflated`, не больше 1 ГиБ. Потолок `MAX_FUEL_CEILING = 10¹²` — **фиксированная константа**: ничто из документа или из ответа гостя не поднимает запуск выше; расчётный максимум — 1,2 × ожидаемый расход, обрезанный этим потолком. Картинки и копии картинок получают собственные базовые бюджеты (`2·10¹⁰`; `10¹¹` для копии, `2,5·10¹¹` для копии полного размера) только если файл по первым байтам — картинка |
| предел вывода | отчёт, просмотр и страница — 64 МиБ; картинка — 40 МиБ; стерильная копия — 64 МиБ плюс длина исходного файла |
| закрепление гостя | `Engine::pinned(wasm, expected_sha256)`: приложение (`arca-jni`, `arca-ffi`) вшивает ожидаемый SHA-256 при сборке, модуль с другим хэшем получает `Status::Fault`. `Engine::new` без ожидаемого хэша закрепляет модуль его же собственным хэшем и годится только для тестов: подменить модуль вместе с хэшем при нём можно |
| проверка стерильной копии на хосте (`check_sterile`) | пересчитывает SHA-256 копии и сверяет с отчётом гостя; у ZIP-копии разбирает архив и отказывает, если имя части содержит `vbaproject.bin`, `activex`, `oleobject`, `embeddings/` или `macrosheets/`. Это растяжка против гостя, который врёт о проверке или забыл самое опасное, а не вторая стерилизация |
| JSON для приложения | страница просмотра не больше 8 МиБ (`MAX_PAGE_JSON_BYTES`), отчёт не больше 32 МиБ (`MAX_REPORT_JSON_BYTES`); строки, которые гость кладёт в отчёт и просмотр, выходят в JSON одной видимой строкой (`display_safe`; тест `strings_the_guest_reports_reach_the_app_as_one_visible_line`); ширины столбцов считаются по реальному числу столбцов, а не по 16 384 на таблицу |
| `Debug` | у `Host`, документа, результата и тела результата печатает виды и размеры, не содержимое и не пароль |

**Что хост делает вне песочницы.** Три вещи, и ни одна не читает содержимое документа:
(1) `sniff_inflated` читает центральный каталог ZIP через `arca-container` и принимает *заявленные* размеры
с недоверием: запись засчитывается не больше чем в `сжатый размер × 100 + 1 МиБ` и не больше 256 МиБ, сумма — не
больше 100 × размера файла и 1 ГиБ, архив с более чем 20 000 записей подсказки не даёт; (2) `check_sterile`
(выше); (3) `arca_image::sniff` по первым байтам решает, дать ли запуску бюджет картинки. Разбор каталога ZIP на хосте — это
парсер вне песочницы, написанный на Safe Rust с теми же проверками, что и в госте; сам он не изолирован, и ошибка в
нём — ошибка на стороне приложения. В 0.2.0 тот же код читал заявленные размеры без оговорок, а заметки обещали
«микросекунды»; время его работы не измерялось ни тогда, ни при последней проверке.

### 4.10 `arca-ffi` и клиент iOS (есть в репозитории, не проверен здесь)

`crates/arca-ffi` — C-мост над теми же `arca-engine`, `Host` и `Engine::pinned`, что у `arca-jni`. `ffi.rs` —
единственный файл с `unsafe` (`unsafe_code = "deny"` в остальном крейте), функции `arca_*` вызывают безопасный
`api.rs` внутри `catch_unwind`; заголовок — `include/arca.h`. Поверх него в `app/` лежит Swift Package `ArcaKit`
(актор-обёртка, модели, экраны SwiftUI: выбор файла, отчёт «Рентгена», просмотр, просмотр картинки, исходники
макросов, стерильная копия, «О проекте» и «Паспорт»), тесты `ArcaKitTests`, скрипты `tools/ios/*` и workflow
`ios.yml` на `macos-14`. Всё это написано владельцем проекта отдельно; **при проверке 0.2.2 не собиралось и не
запускалось** (нужны macOS и Xcode): ни XCFramework, ни `swift build`, ни `swift test`, ни одного запуска на
устройстве. Rust-часть `arca-ffi` входит в workspace и менялась в раундах проверки вместе с `arca-jni` (закрепление гостя по
ожидаемому хэшу), но цели Apple не собирались. `docs/IOS_ARCHITECTURE.md` — проектный документ с описанием
желаемого (расширение «Поделиться», виджеты, уведомления, Secure Enclave); поиск по исходникам `app/` этих
компонентов не нашёл, поэтому читать его как описание готового приложения нельзя.


## 5. Поток данных при открытии документа

1. Приложение получает дескриптор файла (системный выбор файла или «Открыть с помощью»;
   широкого доступа к ФС нет). `arca-jni` читает байты прямо из дескриптора в память ядра:
   в куче Java документа нет.
2. `arca-engine` выбирает лимиты по устройству и вызывает `Sandbox::run` с модулем
   `arca_guest_xray.wasm`, вшитым в `libarca_jni.so`, и его закреплённым SHA-256.
3. Песочница копирует вход в память гостя, гость выполняет `scan`, хост копирует конверт с
   проверкой границ (размер результата не больше предела операции) и уничтожает экземпляр.
4. `decode_report` декодирует `XRayReport` с лимитами и общим бюджетом памяти; `arca-engine` превращает
   его в JSON, который приложение читает страницами (страница ≤ 8 МиБ, отчёт ≤ 32 МиБ).
5. Вердикт `Rejected` → документ не отображается, экран результата объясняет причину.
   Иначе по запросу в **новой** песочнице тот же модуль выполняет `preview` (операция ABI v2
   `Preview3`): разбирает формат и строит `Preview` — разделы, блоки (абзацы, таблицы,
   слайды), уведомления о том, что не показано. Внешние ресурсы не загружаются, ссылки
   остаются данными.
   «Показать страницами» (только PDF) — операция ABI v4 `Render`: страница PDF записывается в
   список примитивов (контуры, текст, отметки картинок, обрезки), приложение рисует его на
   `Canvas`; картинок и шрифтов из документа в приложении нет.
6. «Создать стерильную копию» → `sanitize` (в песочнице, тем же механизмом) →
   повторный рентген в госте → проверка на хосте (SHA-256 копии против отчёта, имена частей ZIP) →
   сохранение через системный диалог.
7. Закрытие документа → буферы обнуляются, дескрипторы освобождаются.

Правила:
* только чистый Rust, никаких `*-sys`, `cc`, `cmake`, `bindgen` (`deny.toml`,
  `tools/check-unsafe.sh`);
* прямые зависимости закреплены точно (`=x.y.z`), функции по умолчанию
  выключены, включено только проверенное;
* **`Cargo.lock`** (D-1) закоммичен, у каждого пакета crates.io в нём есть контрольная сумма;
  `tools/check-lockfile.sh` (`arca-devtools check-lockfile`) проверяет это в CI, сборки и тесты идут с `--locked`. Список
  библиотек, которые попадают в APK, не ведётся вручную: `arca-devtools third-party` строит
  его (с текстами лицензий) из графа зависимостей `arca-jni`; если у библиотеки нет
  лицензии, выпуск останавливается;
* **закрепление гостя** (D-2): приложение вшивает `arca_guest_xray.wasm` в `libarca_jni.so` и
  вместе с ним — его SHA-256 (`ModulePin`, считается в `build.rs`); песочница не запустит модуль с
  другим хешем. Гость собирается в CI с `--locked`, закреплённым `rust-toolchain.toml` и профилем
  `guest`; `tools/build-guest.sh` печатает `sha256sum` модуля и проверяет отсутствие секции
  импортов. Хэш виден в «Диагностике» и печатается в заметках релиза. Задание CI
  `reproducible` (`tools/check-reproducible.sh`) собирает гостя и хостовую `libarca_jni.so`
  дважды — из двух копий дерева в каталогах с разными именами — и требует одинаковый SHA-256.
  Задание `reproducible-guest` собирает гостя ещё и в двух дистрибутивах (`ubuntu:22.04`, `debian:bookworm`: свой rustup, `--locked`,
  `--remap-path-prefix`, `SOURCE_DATE_EPOCH`) и требует одинаковый SHA-256; побитовая воспроизводимость всего APK не заявляется
  (см. docs/RELEASING.md, «Воспроизводимость»).
  Между разными машинами/образами и для APK целиком (NDK, подпись) сравнения не было;
* `cargo deny check all` в CI: лицензии, RustSec advisories, запреты, источники;
* зависимости содержат внутренний `unsafe` (`wasmi`, `quick-xml`, `memchr`,
  `zeroize`). `forbid(unsafe_code)` распространяется на код Arca; доверие к
  зависимостям — осознанное и минимальное, их список — вся доверенная база.

## 8. Решения и отклонения

| решение | обоснование |
|---|---|
| `wasmi`, а не `wasmtime` | iOS не допускает JIT; интерпретатор проще аудировать |
| одна копия входа в гостя и одна копия результата вместо zero-copy | у Wasm-гостя нет доступа к памяти хоста по определению; копия — цена изоляции. На стыке приложения и Rust копий меньше: документ идёт из файлового дескриптора прямо в память ядра, а в Java возвращаются только маленькие страницы результата |
| модуль компилируется заново при каждом запуске | полная эфемерность; около 16 мс. Кэширование проверенного `Module` возможно позже без ослабления изоляции экземпляров |
| запас 1 МиБ в проверке коэффициента сжатия | мелкие однородные XML-части законно сжимаются сильнее 100:1; абсолютный объём ограничен общим бюджетом |
| `deny` вместо `forbid` в `arca-guest-xray` | см. §4.6 |
| `arca-jni` вместо `flutter_rust_bridge` | Android-клиент — нативное приложение без Flutter: меньше кода и зависимостей в доверенной базе, прямой доступ к `ParcelFileDescriptor`. JNI-glue изолирован в одном файле `ffi.rs` (единственный `unsafe` вне таблицы экспортов гостя), вся логика — в безопасном `api.rs`; проверяется тестами на настоящей JVM с `-Xcheck:jni`. Для iOS потребуется свой тонкий мост над тем же `arca-engine` |
| Java без AndroidX и Gradle | цепочка поставок Java-стороны пуста: в APK попадает только код этого репозитория и `libarca_jni.so`; пакет собирается пятью инструментами SDK, а не плагинами. Цена — больше ручного кода и отсутствие Jetpack WindowManager (нет учёта шарнира складных устройств) |
| Wasm-гость вшит в `libarca_jni.so` | приложение запускает только тот гость, с которым собрана библиотека; его хэш виден пользователю и в заметках релиза |
| стерилизатор на месте только для OOXML; остальное — пересборка | в OOXML части вырезаются на месте и результат проверяется повторно. Для ODF и PDF копия строится заново из допустимого (§4.12, §4.13 модели угроз); для DOC/XLS/PPT и RTF — пересборкой в новый OOXML из модели `Preview`, которая теряет вёрстку, поэтому это «копия по просмотру», а не копия документа; картинка — новый PNG из пикселей. Для остальных форматов `SanitizeError::Unsupported` |
| модель `Preview` вместо графа сцены `ArcaRenderTree` | первая версия показывает содержание (абзацы, таблицы, слайды), а не вёрстку страницы: это на порядок проще, проверяемо и достаточно, чтобы прочитать подозрительный документ. Рисование страниц — отдельный этап |
| эвристики в бинарных форматах | VBA stomping, поля Word Binary, PPT-записи — эвристики с низким уровнем ложных срабатываний (проверено на документах LibreOffice). Они дополняют, а не заменяют разбор содержания в `arca-preview` |
| хост читает центральный каталог ZIP и имена частей стерильной копии (вне песочницы) | подсказка о размере распаковки (иначе большая таблица получает «слишком сложно») и растяжка против гостя, который врёт о проверке. Цена — небольшой парсер вне песочницы; он ограничен (§4.9) и ничего не доверяет заявленным размерам |
| фиксированный потолок топлива 10¹² и тот же `FuelPolicy::DEFAULT.max = 4·10¹¹` в песочнице | потолок, выводимый из размеров, которые заявляет документ, позволял бы документу «купить» бюджет; теперь максимум не зависит от файла, а время ограничивают дедлайн и отмена |
| `Engine::pinned` с ожидаемым SHA-256, вшитым при сборке | `ModulePin` из собственного хэша модуля защищает только от подмены между запусками; ожидаемый хэш задаётся там, где собирается приложение |
| клиент iOS нативный (Swift/SwiftUI над C-мостом), а не Flutter | те же причины, что для Android: минимальная доверенная база и пустая цепочка поставок Swift-стороны. Что именно написано и что проверено — §4.10 |
| обнуление памяти | обнуляются буферы, которыми владеет Arca (документ, пароль, результаты, ключи AES/RC4 в `arca-container`), и вся линейная память гостя при `Drop` стража. Это добросовестное, а не гарантированное стирание: копии, которые аллокатор мог оставить при перераспределении `Vec` внутри зависимостей, не стираются; при аварийном завершении процесса страж не выполняется; память гостя стирается целиком, поэтому разбор там безопаснее |
| зашифрованные документы | обнаруживаются (`EncryptedDocument`); без пароля — вердикт `Unverified`. С паролем (ABI v3: он едет в префиксе запроса) гость расшифровывает файл в обычную копию и пускает её через тот же разбор; пароль и ключ остаются в госте. Office 2007/2010+ (у agile-пакета проверяется HMAC `dataIntegrity`) и стандартный PDF-обработчик (неизвестный метод фильтра шифрования — ошибка, а не «без шифрования»); ODF и RC4-бинарные форматы не поддерживаются |
| топливо порциями, а не одним куском | единственный способ дать хосту точку отмены и дедлайна без таймера в госте и без потоков-надзирателей; стоимость — один возврат из интерпретатора на 25·10⁶ операций (практически нулевая) |
| память растёт с размером входа | фиксированные 128 МиБ отвергали законные большие таблицы; потолок остаётся жёстким (1 ГиБ), а для малого файла лимит — около 96 МиБ |
| распаковка точного размера (`inflate_exact`) | выделение ровно заявленного размера и проверка, что поток закончился точно на нём, вместо роста `Vec` вдвое: пиковая память таблицы на 59 % ниже, «лживый» размер обнаруживается без распаковки лишнего |
| собственный разбор XML вместо `quick-xml` | **не принято в Фазе 2.** Измерение показало, что токенизатор `quick-xml` в интерпретаторе стоит ≈ 4 700 топлива на событие (≈ 10× от нативной стоимости); причину внутри `quick-xml`/`memchr` найти не удалось. Это главный резерв производительности гостя; решение (потоковый токенизатор без DOM, свой разбор горячего пути) — в Фазе 3 вместе с парсерами форматов |

## 9. Сборка и проверка

Rust-часть (кроме целей Apple) собирается на любом Linux; на Windows — в WSL (Ubuntu), в каталоге внутри
Linux, а не в `/mnt/c`. Шаги подготовки — в [README](../README.md#сборка) и [RELEASING](RELEASING.md).

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets          # ноль предупреждений
cargo test --workspace
tools/check-unsafe.sh

# Wasm-гость и сквозные тесты в песочнице
cargo build -p arca-guest-xray --target wasm32-unknown-unknown --profile guest
ARCA_REQUIRE_E2E=1 \
ARCA_GUEST_XRAY_WASM=$PWD/target/wasm32-unknown-unknown/guest/arca_guest_xray.wasm \
    cargo test --release -p arca-guest-xray --test e2e_sandbox -- --nocapture
# ARCA_REQUIRE_E2E=1 превращает «тест пропущен» в ошибку; ARCA_CORPUS_DIR=<каталог>
# добавляет сверку гостя с нативным сканером по набору файлов
# (корпус пишет `ARCA_CORPUS_OUT=<каталог> cargo test -p arca-xray dump_corpus`)

# Фаззинг
ARCA_FUZZ_ITERS=30000 ARCA_FUZZ_SEED=1 \
    cargo test --release -p arca-xray mutation_fuzz   # структурные мутации, детерминированно
ARCA_FUZZ_ITERS=30000 ARCA_FUZZ_SEED=1 cargo test --release -p arca-image --test mutation       # декодеры PNG/JPEG/GIF/BMP/EXIF
ARCA_FUZZ_ITERS=30000 ARCA_FUZZ_SEED=1 cargo test --release -p arca-container --test jet_mutation   # базы Access
cd fuzz && cargo +nightly fuzz run scan               # libFuzzer, см. fuzz/README.md

# Android
bash tools/android/check-android.sh      # ресурсы, манифест, API 26/36, чистая Java-логика
ARCA_GUEST_WASM=$PWD/target/wasm32-unknown-unknown/guest/arca_guest_xray.wasm \
ARCA_CORPUS_DIR=$PWD/tests/fixtures bash android/host-test/run.sh   # JNI + контрактные тесты на JVM
# пакет и релиз: .github/workflows/android.yml, tools/android/build-apk.sh, docs/RELEASING.md

# Цепочка поставок
bash tools/check-lockfile.sh
bash tools/check-reproducible.sh         # гость и libarca_jni.so из двух каталогов: одинаковый SHA-256

# iOS — только macOS (не запускалось при проверке 0.2.2)
bash tools/ios/check-ios.sh

# CLI для ручной проверки
cargo run -p arca-xray --example xray -- scan suspicious.docm

```

## 10. Что дальше

* **Сделано.** Фаза 3 (безопасный просмотр OOXML, OLE2, ODF, RTF, PDF, MSG, Access, Visio в песочнице,
  вычислитель формул XLSX, постраничный вид PDF, картинки) и Фаза 4 для Android (`arca-engine`, `arca-jni`,
  приложение, сборка и выпуск). См. [`ANDROID.md`](ANDROID.md) и [`releases/v0.1.0.md`](releases/v0.1.0.md).
* **Рисунок Visio** (геометрия, мастера, 3D): не сделан. `arca-preview::vsdx` показывает текст фигур, данные
  фигур, ссылки и соединения (вставленные просмотром строки помечены `SYNTHETIC`); 3D в VSDX не
  реализован. `arca-preview::vsd` (бинарный) показывает только текст фигур: соединители, данные фигур,
  гиперссылки и мастера **не читаются** — разметка этих кусков не проверена на настоящих файлах, они
  учитываются в уведомлении «не поддержано». Чтобы вернуть их, нужны настоящие `.vsd`-файлы для проверки.
  Access (Jet 3/Jet 4/ACE) читается модулем `arca-preview::access`: таблицы — сохранённые значения;
  запросы — сохранённые строки `MSysQueries` и, только для простого `SELECT`, приближённый SQL с пометкой
  `SYNTHETIC` и уведомлением «не проверено» (раскладка атрибутов взята из описания Jackcess и на запросах
  настоящих баз не сверялась); формы, отчёты, макросы и модули только перечислены.
* **Рисование страниц** (`ArcaRenderTree`-подобная модель с позициями) для всего, кроме PDF: точная
  вёрстка, картинки, диаграммы.
* **Вычислитель формул** уже есть для XLSX (`arca-preview::formula`, модель угроз §4.15); XLS и ODS показывают
  сохранённое.
* **iOS-клиент** над тем же `arca-engine`: код в репозитории есть (§4.10), сборка и проверка на macOS не
  выполнялись.
* **Складные устройства с учётом шарнира и позы** (требует Jetpack WindowManager).
* **Фаза 5.** Расширение фаззинга на парсеры просмотра (каркас `fuzz/` и структурный мутационный
  тест уже есть для сканера, стерилизатора, wire, ZIP, CFB и XML; парсеры просмотра покрыты
  мутационными тестами в самих модулях), дифференциальное тестирование с независимыми
  реализациями, корпус реальных вредоносных образцов в изолированной CI-среде.
